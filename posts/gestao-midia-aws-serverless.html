Gestão de Mídia Corporativa no S3: do File Gateway ao Serverless

Como eliminei a latência do SMB, o caos de upload manual de vídeos e construí uma galeria web serverless com Lambda, Presigned URLs, CloudFront e Cognito.

Dois problemas operacionais reais em uma empresa de beneficiamento mineral: operadores acessando milhares de fotos de blocos de granito via SMB montado sobre File Gateway — lento, inconsistente, sem pré-visualização — e o mesmo operador enviando vídeos de inspeção pelo WhatsApp para um colega subir manualmente no servidor. Esse post documenta como resolvi os dois com uma única arquitetura serverless: galeria web com upload direto ao S3, autenticação via Cognito e entrega via CloudFront.

Resumo direto (TL;DR)#

  • Problema 1: File Gateway + SMB com latência alta, cache inconsistente e zero pré-visualização para fotos de blocos.
  • Problema 2: Upload de vídeo dependia de um operador mandar o arquivo por WhatsApp para outro subir no servidor — processo frágil, sem rastreabilidade, com perda de qualidade.
  • Solução: Galeria web serverless com upload direto ao S3 via Presigned URL, protegida por Cognito, distribuída por CloudFront, orquestrada por Lambda + API Gateway.
  • IaC: AWS SAM — deploy com sam build && sam deploy.
  • Resultado: Operador abre o browser, digita o número do bloco, vê as fotos e faz upload de foto ou vídeo em segundos — sem depender de ninguém.

As duas dores reais#

Dor 1 — File Gateway como interface permanente

O fluxo original: S3 → AWS Storage Gateway (modo File Gateway) → share SMB → montado como unidade de rede no Windows dos operadores. Funciona em cenário de migração gradual. Vira armadilha quando se torna operação permanente.

Com pastas contendo 3.000+ JPEGs por bloco, cada abertura no Windows Explorer gerava listagem síncrona via SMB — levava segundos. O cache local do File Gateway divergia entre operadores que faziam upload simultâneo. Não havia pré-visualização: o operador abria o arquivo, esperava o download completo, revisava, fechava. Para revisão em lote de fotos de produção, completamente inviável.

Dor 2 — Upload de vídeo via WhatsApp

Cada bloco tem um vídeo de inspeção — câmera percorrendo a superfície da pedra, usado pelo time comercial e pela diretoria para apresentar o material a compradores. O processo real era esse:

  • Operador grava o vídeo em campo com o celular.
  • Manda o MP4 por WhatsApp para um colega no escritório.
  • O colega faz download, renomeia e sobe manualmente para a pasta SMB.
  • A pasta SMB sincroniza com o S3 via File Gateway — com delay variável.

Resultado: vídeos comprimidos pelo WhatsApp com perda de qualidade, arquivos com nome errado caindo em blocos errados, zero rastreabilidade de quem subiu o quê e quando, e toda a operação dependendo de duas pessoas disponíveis ao mesmo tempo.

Arquitetura da solução#

Browser (Operador)
    │
    ▼
CloudFront Distribution
    ├── /api/*  ─────►  API Gateway (REST)
    │                        │
    │                        ▼
    │                  Lambda Node.js
    │                  (fotos-manager)
    │                        │
    │             ┌──────────┼───────────┐
    │             ▼          ▼           ▼
    │         ListObjects  Presign    Delete
    │                      URL
    │
    └── /*  ─────►  S3 (frontend estático)

# Upload: browser faz PUT direto ao S3 com Presigned URL
Browser ──PUT──► S3 bucket (mídia)
                  └── FotosGranito/{bloco}/
                      ├── foto_001.jpg
                      ├── foto_001_P.jpg   ← thumbnail gerado no browser
                      └── video_bloco.mp4

Amazon Cognito User Pool
    └── JWT Authorizer no API Gateway (todas as rotas)

Ponto central do design: o arquivo nunca passa pela Lambda. A Lambda gera uma Presigned URL com TTL de 5 minutos. O browser executa o PUT direto ao S3. Isso elimina o limite de payload do API Gateway (10 MB) e o timeout da Lambda — permite upload de vídeos de centenas de MB sem restrição da camada de aplicação.

Infraestrutura como Código (SAM)#

Todo o stack vive em um único template.yaml. A escolha por SAM ao invés de Terraform puro foi pragmática: as abstrações nativas para Lambda + API Gateway reduzem o boilerplate para esse padrão. 

# template.yaml — estrutura principal

AWSTemplateFormatVersion: '2010-09-09'
Transform: AWS::Serverless-2016-10-31

Globals:
  Api:
    BinaryMediaTypes:
      - 'image~1jpeg'
      - 'video~1mp4'
    Cors:
      AllowMethods: "'GET,POST,DELETE,OPTIONS'"
      AllowHeaders: "'Content-Type,Authorization'"
      AllowOrigin: "'https://app.empresa.com'"

Resources:
  MediaManagerFunction:
    Type: AWS::Serverless::Function
    Properties:
      Handler: src/index.handler
      Runtime: nodejs20.x
      MemorySize: 512
      Timeout: 30
      Environment:
        Variables:
          DEST_BUCKET: !Ref MediaBucket
      Policies:
        - Statement:
            # ATENÇÃO: ListBucket no ARN do BUCKET (sem /*).
            # Com /* retorna AccessDenied genérico — erro clássico.
            - Effect: Allow
              Action: s3:ListBucket
              Resource: !Sub "arn:aws:s3:::${MediaBucket}"
              Condition:
                StringLike:
                  s3:prefix: "FotosGranito/*"
            - Effect: Allow
              Action:
                - s3:GetObject
                - s3:PutObject
                - s3:DeleteObject
              Resource: !Sub "arn:aws:s3:::${MediaBucket}/FotosGranito/*"
      Events:
        # Rota genérica para fotos e frontend
        ApiProxy:
          Type: Api
          Properties:
            Path: /{proxy+}
            Method: ANY
        # Rotas de vídeo declaradas EXPLICITAMENTE
        # Se omitir, o API GW não roteia — sem erro no deploy, sem log claro
        PresignUploadVideo:
          Type: Api
          Properties:
            Path: /presign-upload-video/{bloco}/{filename}
            Method: GET
        NotifyVideo:
          Type: Api
          Properties:
            Path: /notify-video/{bloco}
            Method: POST
        ListVideos:
          Type: Api
          Properties:
            Path: /videos/{bloco}
            Method: GET

Lambda: estrutura das rotas#

A Lambda serve o frontend HTML embutido e expõe todas as rotas via roteamento manual — sem framework. O código usa AWS SDK v3 (@aws-sdk/client-s3 + @aws-sdk/s3-request-presigner). 

# Mapa de rotas (src/index.js)

GET  /                              → HTML da galeria (embutido na Lambda)
GET  /fotos/:bloco                  → ListObjectsV2 + Presigned URLs GET (1h)
GET  /presign-upload/:bloco/:file   → Presigned URL PUT para foto (5min)
GET  /videos/:bloco                 → ListObjectsV2 filtrando .mp4 + Presigned URLs GET
GET  /presign-upload-video/:bloco/:file → Presigned URL PUT para vídeo (5min)
POST /notify-video/:bloco           → confirma upload concluído, atualiza estado da UI
DELETE /foto                        → DeleteObject no S3
# Geração de Presigned URL (foto ou vídeo — mesma função)

const { S3Client, PutObjectCommand } = require("@aws-sdk/client-s3");
const { getSignedUrl } = require("@aws-sdk/s3-request-presigner");

const s3 = new S3Client({ region: process.env.AWS_REGION });

async function gerarPresignedUpload(bloco, filename, contentType) {
  const key = `FotosGranito/${bloco}/${filename}`;
  const cmd = new PutObjectCommand({
    Bucket: process.env.DEST_BUCKET,
    Key: key,
    ContentType: contentType,  // 'image/jpeg' ou 'video/mp4'
  });
  // URL expira em 5 minutos. Expirada = upload falha com 403.
  return getSignedUrl(s3, cmd, { expiresIn: 300 });
}

Upload de vídeo: fluxo completo#

O upload de vídeo segue o mesmo padrão da foto com uma etapa extra de notificação. Como vídeos chegam a centenas de MB, o browser confirma para a Lambda que o PUT foi concluído — isso atualiza a UI sem depender de polling no S3 ou evento S3 assíncrono. 

# Fluxo no browser (JavaScript)

async function uploadVideo(bloco, file) {
  atualizarProgresso('Solicitando autorização...');

  // 1. Solicita Presigned URL PUT à Lambda
  const res = await fetch(`${API}/presign-upload-video/${bloco}/${file.name}`, {
    headers: { Authorization: `Bearer ${token}` }
  });
  const { url } = await res.json();

  atualizarProgresso('Enviando vídeo diretamente ao S3...');

  // 2. PUT direto ao S3 — não passa pela Lambda nem pelo API Gateway
  const upload = await fetch(url, {
    method: 'PUT',
    body: file,
    headers: { 'Content-Type': 'video/mp4' }
  });
  if (!upload.ok) throw new Error('Falha no upload');

  // 3. Notifica Lambda: upload concluído
  await fetch(`${API}/notify-video/${bloco}`, {
    method: 'POST',
    headers: { Authorization: `Bearer ${token}`, 'Content-Type': 'application/json' },
    body: JSON.stringify({ filename: file.name, size: file.size })
  });

  atualizarProgresso('Vídeo disponível na galeria.');
}

Com esse fluxo, o operador abre a galeria no celular em campo, seleciona o vídeo gravado, aguarda o upload e o vídeo aparece imediatamente na galeria — identificado com seu usuário Cognito. Fim do WhatsApp, fim do intermediário.

Thumbnails gerados no cliente#

Cada foto precisa de uma versão thumbnail (_P.jpg) usada como capa em outros sistemas internos. A geração foi implementada via Canvas API no browser, antes do upload do original — sem Lambda de processamento, sem fila de eventos, sem custo adicional de compute. 

# Geração de thumbnail via Canvas API

async function gerarThumbnail(file) {
  return new Promise((resolve) => {
    const img  = new Image();
    const burl = URL.createObjectURL(file);
    img.onload = () => {
      const canvas = document.createElement('canvas');
      const ratio  = Math.min(300 / img.width, 300 / img.height);
      canvas.width  = img.width  * ratio;
      canvas.height = img.height * ratio;
      canvas.getContext('2d').drawImage(img, 0, 0, canvas.width, canvas.height);
      canvas.toBlob(resolve, 'image/jpeg', 0.7);
      URL.revokeObjectURL(burl);
    };
    img.src = burl;
  });
}

// Fluxo de upload: original → thumbnail com sufixo _P
const thumb     = await gerarThumbnail(file);
const thumbName = file.name.replace('.jpg', '_P.jpg');
const thumbUrl  = await getPresignedUpload(bloco, thumbName, 'image/jpeg');
await fetch(thumbUrl, { method: 'PUT', body: thumb, headers: { 'Content-Type': 'image/jpeg' } });

CloudFront: dois origins, uma URL, um problema de ordem#

O CloudFront unifica TLS, CORS e cache em um único ponto de entrada:

  • /api/* → origin do API Gateway, TTL = 0, sem cache
  • /* → origin do S3 com frontend estático

Problema real encontrado: um behavior configurado para *.mp4 com cache agressivo (para entrega de vídeos) estava interceptando requests de /api/presign-upload-video/57816/video.mp4 antes de chegar ao API Gateway. O browser recebia o binário do S3 ao invés do JSON com a Presigned URL. O erro era silencioso — status 200, mas body corrompido.

A correção foi garantir que o behavior /api/* tenha número de prioridade menor (mais prioritário) do que qualquer pattern de extensão de arquivo. Na console do CloudFront, número menor = maior prioridade.

Modelo de segurança: Cognito + JWT Authorizer#

Toda rota da API é protegida por um Cognito User Pool Authorizer no API Gateway. O JWT é validado antes de invocar a Lambda — requests sem token retornam 401 sem custo de invocação.

Dois grupos no User Pool, autorização granular feita pela Lambda via claim cognito:groups:

  • operadores: listagem, visualização, upload de foto e vídeo. Sem delete.
  • gestores: acesso completo, incluindo delete e listagem cruzada de blocos.

O API Gateway só valida autenticação. A autorização granular fica na Lambda — esse é o ponto de equilíbrio correto. Colocar regras de negócio no API Gateway cria acoplamento que você vai pagar caro quando a lógica de acesso evoluir.

Problemas reais que custaram tempo#

  • Template literals quebrando o HTML embutido na Lambda: o frontend é servido como string via html.push(). Usar backticks dentro do HTML causava SyntaxError em runtime — o parser da Lambda confunde os delimitadores. Solução: concatenação de strings em todo o HTML gerado, sem backtick, sem exceção.
  • Div nesting invisível: ao adicionar novos painéis de UI via push, uma </div> ausente colapsa todos os painéis subsequentes dentro do painel errado. O browser renderiza algo — só que errado. Detecção via script Python que rastreia profundidade de div no arquivo inteiro.
  • ListBucket no ARN errado: s3:ListBucket precisa do ARN do bucket sem /*. Inversão retorna AccessDenied genérico. Trinta minutos olhando para o lugar errado antes de perceber.
  • Rotas de vídeo ausentes no SAM template: o API Gateway não roteia paths não declarados explicitamente. O deploy não falha, o log não diz nada claro — o endpoint simplesmente retorna 403. Solução: declarar cada rota de vídeo como evento separado na função.

Checklist de implementação#

  • ☑ IAM: ListBucket no ARN do bucket (sem /*), object actions no ARN com prefixo restrito
  • ☑ CORS do bucket S3 restrito ao domínio da aplicação — nunca *
  • ☑ Presigned URL: TTL 5 min para upload, 1h para visualização
  • ☑ JWT Authorizer do Cognito em todas as rotas
  • ☑ Rotas de vídeo declaradas explicitamente no SAM template
  • ☑ CloudFront: behavior /api/* com prioridade maior que patterns de extensão
  • ☑ Upload sempre direto ao S3 via Presigned URL — nunca proxy via Lambda
  • ☑ Thumbnail gerado no cliente antes do upload (sem Lambda de processamento)
  • ☑ Notificação pós-upload de vídeo para sincronizar estado da UI
  • ☑ samconfig.toml versionado — zero flags manuais no deploy a partir do segundo run

Conclusão#

O File Gateway foi o ponto de partida certo para migração gradual — mas usá-lo como interface permanente de operação criou atrito acumulado que ninguém media porque estava normalizado. A galeria serverless eliminou a latência SMB, o processo de vídeo via WhatsApp e a dependência de intermediários. O operador hoje opera de forma autônoma, de qualquer dispositivo, com rastreabilidade completa via Cognito. O próximo passo natural é um trigger S3 (s3:ObjectCreated) disparando um SNS para notificar o time comercial automaticamente quando um novo vídeo de bloco entra — sem nenhuma mudança no fluxo do operador.
