Portal corporativo serverless com 10 aplicações internas integradas

Portal interno da Vitória Stone em arquitetura serverless modular: Lambdas especializadas, Cognito com grupos por departamento, DynamoDB single-table, integrações com Firebird (ERP Athenas) e Microsoft Graph. Helpdesk, contracheque, Kaizen, on/offboarding, galeria de mídia — 10 aplicações independentes compartilhando a mesma infra.

De onde isso veio

Em março de 2026 escrevi a primeira versão deste post. Era sobre uma galeria serverless para substituir o AWS Storage Gateway (File Gateway) que a empresa usava para fotografar blocos de mármore e granito. A solução ficou pronta em duas semanas: S3 + Lambda + Cognito + Presigned URLs, custo $5/mês contra os $150/mês da EC2 do File Gateway.

Eu não sabia, mas aquela galeria seria só o primeiro app. Quando a TI percebeu que dava pra subir uma página nova em horas em vez de semanas (porque toda a infra já estava de pé), começaram a pedir: "consegue fazer um helpdesk pra gente parar de receber chamado por WhatsApp?", "consegue puxar holerite do Athenas direto pra o RH não atender ninguém no balcão?", "e um portal de ideias estilo Kaizen?".

Dois meses depois, a "galeria" virou um portal corporativo com 10 aplicações, rodando em uma única Lambda Node.js, com Cognito gerenciando grupos por departamento, DynamoDB armazenando audit log + chamados + ideias, e Microsoft Graph + Firebird ligados em cima.

Print: tela inicial do portal
Grid de aplicações no portal interno (`portal.vitoriastone.com`). Cada card é uma view independente, mostrada de acordo com o grupo Cognito do usuário. Imagem em assets/img/posts/fg-portal.png.

Este post é sobre essa evolução: o que mantive da arquitetura inicial, o que mudou pra suportar 10 apps em vez de 1, e os trade-offs técnicos de servir um monolito serverless em vez de microserviços.

Por que monolito Lambda? Cada app novo é um arquivo de view + uma seção no router. Não é um novo stack, novo pipeline, novo CloudFront, novo Cognito. Iterar é rápido. A Lambda principal hoje tem ~2500 linhas e 80+ endpoints. Reescrever pra microserviços custaria meses e não resolveria nenhum problema real.

Por que SAM e não CDK/Terraform? SAM é YAML puro, lança CloudFormation, e não exige stack de build. Pra um portal serverless mantido por uma pessoa, é o equilíbrio certo entre verbosidade (mais que CDK) e simplicidade (não tem state remoto pra gerenciar como Terraform).

Cognito: o coração do controle de acesso

Quando eram dois usuários admin, autenticação era um detalhe. Quando o portal cresceu para ~120 colaboradores em sete departamentos, ficou claro: cada app precisava ser visível apenas pra quem tem permissão. RH não pode ver chamados de TI, vendedor não pode ver holerite dos outros, etc.

A solução foi um sistema de grupos Cognito mais um atributo custom custom:group no token. Sete grupos default, cada um com uma lista de apps visíveis:

src/permissions.js — definição dos grupos (clique para expandir) 
// ─── Apps disponíveis por grupo ─────────────────────────────
const GROUPS = {
  TI: {
    label: "TI",
    apps: ["*"],          // wildcard: tudo
    isAdmin: true,
  },
  MI: {
    label: "Mercado Interno",
    apps: ["studio", "docs", "loja", "amostras", "chamado", "ideias"],
  },
  ME: {
    label: "Mercado Externo",
    apps: ["studio", "docs", "loja", "amostras", "chamado", "ideias", "ovacao"],
  },
  Producao: {
    label: "Produção",
    apps: ["studio", "stonetrack", "docs", "chamado", "ideias", "rh"],
  },
  Comercial: {
    label: "Comercial",
    apps: ["docs", "loja", "amostras", "chamado", "ideias", "carteira", "rh"],
  },
  RH: {
    label: "Recursos Humanos",
    apps: ["rh", "hr-onoff", "docs", "chamado", "ideias", "mural"],
  },
  Viewer: {
    label: "Somente leitura",
    apps: ["docs", "chamado", "ideias", "mural", "rh"],
  },
};

// ─── Middleware de autorização por app ────────────────────────
function requireApp(appId) {
  return (claims) => {
    const group = claims["custom:group"] || "Viewer";
    const allowed = GROUPS[group]?.apps || [];
    // Wildcard libera tudo
    if (allowed.includes("*")) return true;
    if (allowed.includes(appId)) return true;
    // Grants/denies individuais via custom:perms (JSON)
    try {
      const perms = JSON.parse(claims["custom:perms"] || "{}");
      if (perms.grants?.includes(appId)) return true;
      if (perms.denies?.includes(appId)) return false;
    } catch (_) {}
    return false;
  };
}

module.exports = { GROUPS, requireApp };

No handler de cada rota, o primeiro passo é validar o token e checar o app:

src/index.js — padrão de proteção de rota (clique para expandir) 
const { requireAuth, requireApp } = require("./permissions");

// Ex.: rota do contracheque
if (method === "GET" && path === "/rh/consultar") {
  const claims = await requireAuth(event);  // valida JWT do Cognito
  if (!claims) return jsonResponse(401, { error: "não autenticado" });
  if (!requireApp("rh")(claims)) {
    return jsonResponse(403, { error: "app não liberado para seu grupo" });
  }
  return await handleConsultaRH(event, claims);
}
Por que grupos no token e não em uma tabela? O token JWT chega na Lambda já com o atributo custom:group. Não preciso consultar DynamoDB nem fazer round-trip extra pra autorizar — verifico tudo em memória. Trocar o grupo de alguém exige logout (token expira em 1h) ou forçar refresh, mas isso é aceitável: mudança de grupo é rara.

Refresh silencioso

O IdToken do Cognito dura 1 hora. Para um portal interno onde gente fica logada o dia inteiro, expirar a sessão no meio do trabalho é ruído. Implementei refresh automático no cliente:

Frontend — refresh automático antes da expiração (clique para expandir) 
// ─── Auto refresh do Cognito (50min depois do login) ────────────
function startTokenRefresh(refreshToken) {
  // refresh a cada 50 minutos (IdToken expira em 60)
  setInterval(async () => {
    try {
      const resp = await fetch("/api/auth/refresh", {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({ refreshToken }),
      });
      if (!resp.ok) throw new Error("refresh failed");
      const { idToken } = await resp.json();
      localStorage.setItem("idToken", idToken);
    } catch (err) {
      // Refresh falhou — force re-login
      window.location.href = "/login";
    }
  }, 50 * 60 * 1000);
}

Na Lambda, o endpoint /api/auth/refresh usa AdminInitiateAuth com flow REFRESH_TOKEN_AUTH pra trocar o RefreshToken (que dura 30 dias) por um novo IdToken.

A Lambda principal: roteador de 80+ endpoints

Tem uma decisão controversa aqui que vou defender. O src/index.js é um arquivo de ~2500 linhas que faz routing manual com if encadeados:

src/index.js — estrutura do router (clique para expandir) 
exports.handler = async (event) => {
  const method = event.httpMethod;
  const path = event.path;

  // CORS preflight
  if (method === "OPTIONS") return cors204();

  try {
    // ── Auth/Portal ──
    if (method === "GET" && path === "/")                 return servePortal(event);
    if (method === "GET" && path === "/login")            return serveLoginPage();
    if (method === "POST" && path === "/api/auth/login")  return await handleLogin(event);
    if (method === "POST" && path === "/api/auth/refresh") return await handleRefresh(event);

    // ── VStudio (galeria) ──
    if (method === "GET" && path === "/studio")           return serveStudio(event);
    if (method === "GET" && path === "/list-blocos")      return await handleListBlocos(event);
    if (method === "POST" && path === "/presign-upload")  return await handlePresign(event);
    if (method === "POST" && path.startsWith("/editor-apply")) return await handleEditor(event);
    // ... mais 14 rotas do VStudio

    // ── Chamado ──
    if (method === "GET" && path === "/chamado")          return serveChamado(event);
    if (method === "POST" && path === "/chamado")         return await handleAbrirChamado(event);

    // ── Ideias / Kaizen ──
    if (method === "GET" && path === "/ideias")           return serveIdeias(event);
    if (method === "GET" && path === "/ideias/list")      return await handleListIdeias(event);
    if (method === "POST" && path === "/ideias")          return await handleCriarIdeia(event);
    if (method === "POST" && path.match(/^\/ideias\/[^/]+\/vote$/)) return await handleVoto(event);
    if (method === "POST" && path.match(/^\/ideias\/[^/]+\/status$/)) return await handleStatusIdeia(event);

    // ── RH/Contracheque ──
    if (method === "POST" && path === "/rh/consultar")    return await handleConsultaRH(event);

    // ── HR On/Offboarding ──
    if (method === "POST" && path === "/hr-onoffboarding") return await handleOnboarding(event);

    // ── Admin ──
    if (method === "GET" && path === "/admin/users")      return await handleListUsers(event);
    if (method === "POST" && path === "/admin/users")     return await handleCreateUser(event);
    if (method === "GET" && path === "/audit")            return await handleAudit(event);
    if (method === "GET" && path === "/admin/trash")      return await handleTrash(event);

    // ... 50+ rotas a mais

    return jsonResponse(404, { error: "rota não encontrada" });

  } catch (err) {
    console.error("handler error:", err);
    return jsonResponse(500, { error: "erro interno" });
  }
};

Por que não Express, Fastify, Hono ou qualquer framework? Três motivos:

  1. Cold start. Express adiciona ~80–120ms de import em ARM64. Para um handler que vai responder uma página HTML, isso é tempo útil perdido. Um if/else custa 0ms.
  2. Debug lingüístico. Se algo quebra, eu sei exatamente onde olhar — não tem stack trace passando por 8 middlewares antes do meu código.
  3. Zero dependência. Express subiu para v5, virou breaking change. Meu router não quebra nunca, porque são if nativos do JS.
Quando esse modelo quebra? Se eu tivesse 500+ rotas, ou rotas com matching complexo de path (parâmetros aninhados, versões de API), o if ficaria ilegível. Para ~80 rotas, ainda é trivial. Acima de 200 eu provavelmente migraria pra um router minímo (tipo find-my-way), não um framework completo.

Presigned URL em uma rota multi-tipo

A versão nova da rota de presign suporta foto, vídeo e thumbnail no mesmo endpoint, com tempos de expiração diferentes:

handler de Presigned URL (clique para expandir) 
async function handlePresign(event, claims) {
  const { bloco, fileName, contentType, tipo } = JSON.parse(event.body);

  // Validar acesso ao bloco (RBAC por filial)
  if (!canAccessBloco(claims, bloco)) {
    return jsonResponse(403, { error: "bloco fora da sua filial" });
  }

  // Prefixo varia por tipo
  // tipo = "thumb" | "video" | "edit" | undefined (original)
  const prefix = tipo === "thumb" ? "_P"
              : tipo === "video" ? "video"
              : tipo === "edit"  ? ".edit"
              : "originais";

  const key = `FotosGranito/${bloco}/${prefix}/${fileName}`;

  // Expiração curta para foto, longa para vídeo
  const isVideo = contentType?.startsWith("video/");
  const expiresIn = isVideo ? 900 : 300;  // 15min vs 5min

  const cmd = new PutObjectCommand({
    Bucket: BUCKET,
    Key: key,
    ContentType: contentType,
    Metadata: {
      uploaded_by: claims["cognito:username"],
      bloco: bloco,
    },
  });

  const url = await getSignedUrl(s3, cmd, { expiresIn });

  await logAudit("PRESIGN", claims["cognito:username"], bloco, { key });
  return jsonResponse(200, { url, key, expiresIn });
}
Metadata na key. Quem subiu, qual bloco, qual filial — tudo persiste como S3 Object Metadata. Mesmo se o DynamoDB de audit log corromper, eu tenho o rastro no próprio S3.

Pipeline de vídeo: a segunda Lambda

Aqui apareceu um problema específico. Os operadores filmavam os blocos com celulares Apple, que gravam em HEVC (.mov) — um codec moderno mas que browsers desktop não conseguem reproduzir. Além disso, às vezes o operador esquecia que estava gravando áudio, e a galeria precisava ser silenciosa pra apresentar pro cliente.

A solução: uma segunda Lambda fotos-granito-mute-video que é invocada assincronamente pela Lambda principal logo depois do upload. Ela transcoda HEVC→H264 e remove o áudio. Sai um .mp4 universal.

src-mute/index.js — transcoding (clique para expandir) 
const { S3Client, GetObjectCommand, PutObjectCommand,
        DeleteObjectCommand } = require("@aws-sdk/client-s3");
const { spawn } = require("child_process");
const fs = require("fs");
const path = require("path");

const s3 = new S3Client({});

exports.handler = async (event) => {
  // event.bucket, event.key, event.bloco passados pela manager
  const { bucket, key, bloco } = event;

  const tmpIn  = `/tmp/${path.basename(key)}`;
  const tmpOut = `/tmp/out_${Date.now()}.mp4`;

  // 1. Baixa o original do S3
  const obj = await s3.send(new GetObjectCommand({ Bucket: bucket, Key: key }));
  await streamToFile(obj.Body, tmpIn);

  // 2. FFmpeg: HEVC → H264, sem audio, preset rápido
  await runFfmpeg([
    "-y",
    "-i", tmpIn,
    "-c:v", "libx264",
    "-preset", "veryfast",
    "-crf", "23",
    "-an",                  // sem audio
    "-movflags", "+faststart",
    tmpOut,
  ]);

  // 3. Sobe a versão tratada substituindo o original
  const newKey = key.replace(/\.(mov|MOV)$/, ".mp4");
  await s3.send(new PutObjectCommand({
    Bucket: bucket,
    Key: newKey,
    Body: fs.createReadStream(tmpOut),
    ContentType: "video/mp4",
    Metadata: { transcoded: "true", original: key },
  }));

  // 4. Remove o HEVC original se transcoding deu bom
  if (newKey !== key) {
    await s3.send(new DeleteObjectCommand({ Bucket: bucket, Key: key }));
  }

  // Limpa /tmp
  fs.unlinkSync(tmpIn);
  fs.unlinkSync(tmpOut);

  return { ok: true, key: newKey };
};

function runFfmpeg(args) {
  return new Promise((resolve, reject) => {
    const proc = spawn("/opt/bin/ffmpeg", args);
    proc.stderr.on("data", (d) => console.log(d.toString()));
    proc.on("close", (code) => code === 0 ? resolve() : reject(new Error(`ffmpeg exit ${code}`)));
  });
}

Invocação assíncrona (fire-and-forget)

Na manager, depois do upload registrado, eu disparo a mute-video sem esperar resposta:

manager invoca mute assíncrono (clique para expandir) 
const { LambdaClient, InvokeCommand } = require("@aws-sdk/client-lambda");
const lambda = new LambdaClient({});

async function fireAndForgetMute(bucket, key, bloco) {
  // Só vídeo (MOV/MP4) entra na fila de muting
  if (!/\.(mov|mp4)$/i.test(key)) return;

  await lambda.send(new InvokeCommand({
    FunctionName: "fotos-granito-mute-video",
    InvocationType: "Event",   // ★ assíncrono, não espera resposta
    Payload: Buffer.from(JSON.stringify({ bucket, key, bloco })),
  }));
}
Por que não S3 Event Notification direto? Considerei. O problema: s3:ObjectCreated:* dispara para todos os PUTs no bucket, inclusive thumbnails e arquivos de edição. Filtrar por prefixo/sufixo na config do bucket é limitado (não consigo combinar prefixo + ContentType). Invocar manualmente da manager me dá controle total sobre quando disparar.

Helpdesk: do WhatsApp para ticket rastreado

Print: tela de abrir chamado
Helpdesk interno com categoria, prioridade, descrição e anexo opcional. assets/img/posts/fg-chamado.png.

Antes do portal, chamado de TI funcionava assim: o colaborador mandava WhatsApp pro analista, que às vezes anotava em planilha, às vezes esquecia, às vezes resolvia direto sem registro. Resultado: zero métrica de SLA, zero histórico, zero priorizaqo.

O app chamado é uma das views mais simples do portal, mas resolveu mais problema operacional que muito sistema caro. Cada chamado vira um item no DynamoDB ChamadosTable:

A PK CHAMADO#2026-05 garante que todos os chamados do mês ficam na mesma partition (DynamoDB Query barata). Os GSIs respondem perguntas operacionais:

  • status-criadoEm-index: lista chamados abertos ordenados por mais antigo (priorizar).
  • assignedTo-criadoEm-index: histórico de um analista (relatório individual).

Notificação no Telegram (sem SNS)

Quando um chamado é aberto, em vez de configurar SNS → SES → inbox sobrecarregada, eu uso um bot do Telegram. O time de TI recebe na hora:

notificação Telegram (sem SDK) (clique para expandir) 
async function notifyTelegram(chamado) {
    const TOKEN  = await getConfig("telegram/bot-token");
    const CHATID = await getConfig("telegram/chat-id-ti");
    if (!TOKEN || !CHATID) return; // sem config? não quebra o fluxo

    const url = `https://api.telegram.org/bot${TOKEN}/sendMessage`;
    const msg = `*Novo chamado* · *${chamado.prioridade}*\n`
              + `👤 ${chamado.usuario}\n`
              + `📌 ${chamado.titulo}\n`
              + `💬 ${chamado.descricao.slice(0, 120)}...\n`
              + `\u{1F517} portal.vitoriastone.com/admin/chamados/${chamado.id}`;

    try {
      await fetch(url, {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({
          chat_id: CHATID,
          text: msg,
          parse_mode: "Markdown",
        }),
      });
    } catch (err) {
      // Fire-and-forget: não quebra a abertura do ticket
      console.error("Telegram notify failed:", err.message);
    }
}
Por que Telegram e não SES/SNS? O time de TI já usa Telegram pra comunicação interna. SES/SNS exigiria que alguém acompanhasse o email. Telegram é em tempo real, todo mundo já tem instalado, e o token gratuito do BotFather não tem rate limit relevante pra esse volume (~10 chamados/dia).

Aqui é onde a arquitetura saiu da zona de conforto serverless. O ERP Athenas roda em uma EC2 com Firebird 5.0 dentro da VPC corporativa. O Lambda da função principal precisa consultar esse Firebird para gerar holerite, mas Lambda fora da VPC não enxerga o Firebird (que está em subnet privada).

Tinha duas opções:

OpçãoPrósContras
Botar a Lambda inteira dentro da VPC Solução direta Cold start +600ms (ENI provisioning), aumenta custo NAT
Separar em uma segunda Lambda RH dentro da VPC, chamada só quando necessário Lambda principal continua aréna, sem cold start extra Mais um arquivo, mais um deploy
Bridge via API REST na própria EC2 Sem mudança em Lambda Mais um serviço pra manter (Nginx + Node na EC2)

Acabei escolhendo uma quarta opção que não tinha pensado: chamar o Firebird via outra integração que já existe. A empresa já tinha uma EC2 com um serviço REST exposto internamente para o LeverPro (outra integração que documentei neste post). Reusei o mesmo endpoint, com um path novo, com allowlist de IPs (somente o Egress IP do Lambda).

src/paystub_query.js — consulta Firebird via REST proxy (clique para expandir) 
const PROXY_URL = process.env.ATHENAS_PROXY_URL;
// Ex: https://leverpro.vitoriastone.com.br/internal/athenas/paystub

async function fetchPaystub({ cpf, dataNascimento, competencia }) {
  // Token vai no SSM como SecureString
  const token = await getConfig("athenas/internal-token");

  const resp = await fetch(`${PROXY_URL}?` + new URLSearchParams({
    cpf, dataNascimento, competencia,
  }), {
    method: "GET",
    headers: { "X-Internal-Token": token },
  });

  if (resp.status === 404) return null;
  if (!resp.ok) throw new Error(`athenas proxy ${resp.status}`);
  return await resp.json();
}

module.exports = { fetchPaystub };
Cuidado com PII em log. Holerite tem salário, CPF, dependêntes — PII pesado. O console.log default do Lambda manda tudo pra CloudWatch Logs. Aqui eu loguei apenas o CPF mascarado (`***.***.123-**`) e nenhum valor financeiro. CloudWatch Logs tem retenção de 30 dias mas a regra LGPD é não expor desnecessariamente.

endpoint de voto idempotente (clique para expandir) 
async function handleVoto(event, claims) {
  const ideiaId = event.path.split("/")[2];
  const user = claims["cognito:username"];

  // Idempotente: cada usuário só vota uma vez por ideia
  // Implementado via SK composta: VOTE#<ideia-id>#<username>
  const item = {
    pk: { S: `IDEIA#${ideiaId}` },
    sk: { S: `VOTE#${user}` },
    user: { S: user },
    ts: { S: new Date().toISOString() },
  };

  try {
    await ddb.send(new PutItemCommand({
      TableName: "fotos-granito-ideias",
      Item: item,
      // Falha se já existe (idempotência)
      ConditionExpression: "attribute_not_exists(sk)",
    }));
    return jsonResponse(200, { voted: true });
  } catch (err) {
    if (err.name === "ConditionalCheckFailedException") {
      // Já tinha votado — remove (toggle)
      await ddb.send(new DeleteItemCommand({
        TableName: "fotos-granito-ideias",
        Key: { pk: item.pk, sk: item.sk },
      }));
      return jsonResponse(200, { voted: false });
    }
    throw err;
  }
}
Por que ConditionExpression? Sem ela, se um usuário clica duas vezes rapidamente (race condition no front), ele "vota" duas vezes. Com attribute_not_exists(sk), o segundo PutItem falha e o handler trata como toggle (remove). Idempotência gratuita.

Audit log como single-table design

Cada ação (login, upload, delete, edit, voto, chamado aberto) escreve no DynamoDB:

schema audit log (clique para expandir) 
// PK = AUDIT#<date-iso>     (ex: AUDIT#2026-05-26)
// SK = <timestamp>#<rand>   (ex: 2026-05-26T13:42:10.341Z#a1b2c3)
//
// Atributos:
//   action: "UPLOAD" | "DELETE" | "LOGIN" | "VOTE" | "CHAMADO_OPEN" | ...
//   user:   "matheus.nascimento"
//   bloco:  "58731" | null
//   ip:     "201.x.x.x"  (User-Agent X-Forwarded-For)
//   ua:     navegador
//   details: JSON com payload da ação
//   ttl:    epoch + 90d  (auto-expira)

async function logAudit(action, user, bloco, details = {}) {
  const now = new Date().toISOString();
  const rand = Math.random().toString(36).slice(2, 8);

  try {
    await ddb.send(new PutItemCommand({
      TableName: AUDIT_TABLE,
      Item: {
        pk: { S: `AUDIT#${now.slice(0, 10)}` },
        sk: { S: `${now}#${rand}` },
        action: { S: action },
        user: { S: user || "anonymous" },
        bloco: { S: bloco || "N/A" },
        ts: { S: now },
        details: { S: JSON.stringify(details).slice(0, 4000) },
        ttl: { N: String(Math.floor(Date.now() / 1000) + 90 * 86400) },
      },
    }));
  } catch (err) {
    // Falha de audit não deve quebrar a operação do usuário
    console.error("audit failed:", err.message);
  }
}
TTL não é instantâneo. O DynamoDB TTL deleta dentro de até 48h depois que o atributo expira. Se você quiser ver registros sumirem na hora certa, não é pelo TTL. Para audit log de 90 dias isso não é problema; pra compliance rígido, considere uma Lambda cron que faz delete explicito.

Microsoft Graph: integração com OneDrive/SharePoint

Dois apps do portal (Ovação e Planilhas/Telefones) precisam ler documentos que vídeo no OneDrive/SharePoint corporativo. A integração usa Microsoft Graph API com app-only auth (client_credentials).

Microsoft Graph — obter token e listar arquivos (clique para expandir) 
// ─── Cache do token (50 min, validá em 60) ───────────────
let _tokenCache = { value: null, exp: 0 };

async function getGraphToken() {
  const now = Date.now();
  if (_tokenCache.value && _tokenCache.exp > now) return _tokenCache.value;

  const TENANT_ID = await getConfig("onedrive/tenant_id");
  const CLIENT_ID = await getConfig("onedrive/client_id");
  const CLIENT_SECRET = await getConfig("onedrive/client_secret");

  const url = `https://login.microsoftonline.com/${TENANT_ID}/oauth2/v2.0/token`;
  const body = new URLSearchParams({
    client_id: CLIENT_ID,
    client_secret: CLIENT_SECRET,
    scope: "https://graph.microsoft.com/.default",
    grant_type: "client_credentials",
  });

  const resp = await fetch(url, {
    method: "POST",
    headers: { "Content-Type": "application/x-www-form-urlencoded" },
    body,
  });
  const json = await resp.json();
  if (!resp.ok) throw new Error(`graph token: ${JSON.stringify(json)}`);

  _tokenCache = { value: json.access_token, exp: now + 50 * 60 * 1000 };
  return json.access_token;
}

async function listOvacao(folderPath) {
  const token = await getGraphToken();
  const DRIVE_ID = await getConfig("onedrive/drive_id");
  const url = `https://graph.microsoft.com/v1.0/drives/${DRIVE_ID}/root:/Ovacao/${folderPath}:/children`;

  const resp = await fetch(url, {
    headers: { Authorization: `Bearer ${token}` },
  });
  const json = await resp.json();
  return json.value || [];
}
Token cache é obrigatório. Sem cache, cada chamada ao Graph faz uma round-trip pro login.microsoftonline.com só pra pegar token novo. Cold start vira ~800ms. Com cache, fica em ~80ms.

  • Timeout maior. Relatório pode demorar 30-60s. A manager tem timeout de 30s.

CloudFront: dois domínios, uma origem

O portal tem dois domínios públicos:

  • portal.vitoriastone.com — portal interno
  • studio.vitoriastone.com — VStudio "white-label" pro comercial mostrar pro cliente sem expor a marca interna

Ambos batem na mesma distribuição CloudFront, mas são roteados pra rotas diferentes na Lambda usando uma CloudFront Function:

scripts/cloudfront/rewrite.js — CloudFront Function de URL rewrite (clique para expandir) 
function handler(event) {
  const request = event.request;
  const host = request.headers.host?.value || "";
  const uri = request.uri;

  // studio.vitoriastone.com → reescreve / para /studio
  if (host.startsWith("studio.")) {
    if (uri === "/" || uri === "") {
      request.uri = "/studio";
    } else if (!uri.startsWith("/studio") && !uri.startsWith("/api")
            && !uri.startsWith("/assets")) {
      request.uri = "/studio" + uri;
    }
  }

  // portal.vitoriastone.com → mantém default (vai pro portal/login)

  return request;
}
CloudFront Functions vs Lambda@Edge. Pra URL rewrite simples (string match, sem network call), CloudFront Functions é ordens de magnitude mais barata: $0.10/million invocations vs $0.60 do Lambda@Edge. Restrição é que ela roda em 1ms e não pode chamar APIs externas. Para qualquer Lógica que precise de I/O, use Lambda@Edge.

Behaviors com ordem de prioridade

CloudFront Distribution
├── Behavior 0 (mais específico): /api/*       → API Gateway, cache off
├── Behavior 1:                      /assets/*    → S3 OAC, cache 24h
├── Behavior 2:                      /espelho/*   → API Gateway, cache 5min
└── Behavior 3 (default):            /*           → API Gateway, cache off

O behavior /espelho/* é o único que cacheia conteúdo dinâmico. A página compartilhável do bloco no WhatsApp pode ser cacheada por 5 minutos — trafic spike de "vários clientes abrindo o mesmo espelho" não derruba a Lambda.

cache de SSM com TTL (clique para expandir) 
const ssmCache = {};
const SSM_TTL = 5 * 60 * 1000;  // 5 minutos

async function getConfig(paramName) {
  const now = Date.now();
  const cached = ssmCache[paramName];
  if (cached && (now - cached.ts) < SSM_TTL) return cached.value;

  try {
    const resp = await ssm.send(new GetParameterCommand({
      Name: `/vstudio/${paramName}`,
      WithDecryption: true,
    }));
    ssmCache[paramName] = { value: resp.Parameter.Value, ts: now };
    return resp.Parameter.Value;
  } catch (err) {
    console.warn(`SSM /vstudio/${paramName} missing:`, err.message);
    return null;
  }
}
Cuidado com IAM no SSM. A política da Lambda dá ssm:GetParameter APENAS pra arn:aws:ssm:*:*:parameter/vstudio/*. Sem o prefixo restrito, qualquer SSM da conta vira potencial vazamento. Se você compartilha a conta com outros projetos, isso é crítico.

Problemas reais que aprendi por queimar tempo

1. Lambda na VPC quebrou o cold start

Quando tentei a primeira solução "põe a Lambda dentro da VPC pra acessar Firebird", o cold start saiu de 250ms pra 900ms. ENI Hyperplane resolveu boa parte (~500ms), mas não é zero. O proxy REST elimina o problema totalmente, ao custo de uma EC2 extra (que já existia por outro motivo).

2. Cognito email com `<` quebra HTML

O Cognito tem um template de email pra "esqueci minha senha", e ele aceita HTML. Mas se você usar < ou > em algum lugar (ex: descrevendo um código), o template quebra silenciosamente no servidor da AWS — o email sai vazio, sem erro nos CloudWatch Logs. Levou 2 horas pra descobrir.

3. DynamoDB GSI sem provisioning errado de capacidade

Os primeiros GSIs eu criei com Projection: KEYS_ONLY pra economizar. Resultado: toda Query no GSI tinha que fazer um GetItem extra pra cada resultado, multiplicando reads RCU. Migrei pra Projection: ALL em todos os GSIs críticos. Custo: 2x espaço de armazenamento (irrelevante a $0.25/GB-mês). Ganho: 10x menos reads.

4. CloudFront Function bloqueia se exceder 1ms

Tentei adicionar regex complexa na CF Function. Erro silencioso: requests começaram a voltar com 503. CloudWatch não mostra erro. Só vendo o "Function Throttled" no console que descobri. Simplifiquei a regex e voltou.

5. Microsoft Graph nega permissões em escopos errados

O app no Entra precisava de Files.Read.All (Application, não Delegated) + admin consent. Sem o consent, o token sai sem o escopo silenciosamente e a chamada na Graph dá 403 "Insufficient privileges". A mensagem não diz o óbvio: "vá pedir consent ao Global Admin".

6. setTimeout dentro de handler async é perigoso

Em um lugar usei setTimeout(() => logAudit(...), 0) achando que estava deixando assíncrono. A Lambda finalizava antes do timeout disparar — o audit nunca era escrito. Para fire-and-forget em Lambda, ou você await direto ou usa InvocationType: Event de outra Lambda. Nunca confie em setTimeout.

Conclusão

O que aprendi montando esse portal: "monolito serverless" parece anti-padrão, mas pra um time de uma pessoa é o que destrava velocidade. A única Lambda principal é o ponto de extensão; cada app novo é uma view + algumas rotas + um middleware de permissão. Sem novo pipeline, sem novo Cognito, sem novo CloudFront. Adicionei 9 apps em 2 meses sem mudar a infra base.

A pergunta clássica de revisor de arquitetura é: "e quando você sair, quem mantém?". A resposta é honesta: HTML+JS vanilla, SAM em YAML, e um router de if é o código mais legível possível pra qualquer dev júnior. Sem build step, sem decorators mágicos, sem container customizado. Quem entrar consegue ler em uma tarde.

Se você está pensando em montar algo parecido pra empresa — um portal interno que cresce app por app sem virar custo — serverless monolítico com SAM é uma escolha defensável. Quando o portal crescer pra centenas de rotas ou multi-tenant de verdade, aí vale a pena olhar microsserviços, App Runner, ECS Fargate. Até lá o overhead de modular não se paga.
