Aplicação para limpeza automática de caixas Microsoft 365

Ferramenta interna que monitora quota de caixas Microsoft 365 e dispara limpeza automática de e-mails antigos para o Online Archive. Usa MRM Retention Policy + ManagedFolderAssistant (caminho oficial recomendado pela Microsoft) em vez de EWS bulk_move — processa server-side sem rate limit. Backend FastAPI + Python, frontend Next.js 16, autenticação por certificado no Exchange Online PowerShell.

O problema das caixas cheias

Microsoft 365 vende caixa de 2GB (Exchange Online Plan 1) ou 50GB (Plan 2). O que ninguém fala é que chegando perto do limite, a caixa trava — nem envia, nem recebe. Usuário descobre na cara do cliente que perdeu uma negociação por isso.

Na empresa, saíram 11 mailboxes "no alerta" e 2 "críticas" (>90%). O caminho clássico que toda equipe de TI tenta primeiro:

  1. Outlook desktop manual: usuário abre, seleciona mil e-mails, arrasta pro Online Archive. Inviavel pra milhares de itens.
  2. EWS bulk_move via script: roda batches de PowerShell. Funciona, mas... Microsoft throttles EWS app em ~5 itens/segundo. 13 horas pra 2000 itens.
  3. Microsoft Graph /messages/move: não suporta moves pro Online Archive. Retorna 404 "Item exists in archive mailbox".

Depois de uma noite olhando documentação, achei o caminho oficial recomendado pela Microsoft pra esse cenário: MRM Retention Policy + Managed Folder Assistant. O servidor processa internamente, sem passar por API exposta — sem rate limit do app.

O resultado: caixa da Ana Marcal foi de 66k itens / 43.93GB pra 58k itens / 38GB em 8 horas — e os 5.5GB que sobraram foram movidos pro Online Archive, não deletados. Mesmo resultado de 13h via EWS, em menos tempo e zero throttle.

O caminho oficial: MRM Retention Policy

O que poucos artigos de blog explicam: retention policy + retention tag é o próprio mecanismo da Microsoft pra mover/deletar e-mails baseado em idade. Quando você configura, o próprio servidor processa — não é sua app remotamente fazendo move.

Workflow:

  1. Cria retention tag com a ação MoveToArchive e idade mínima (ex.: 24 meses).
  2. Cria retention policy que contém a tag.
  3. Aplica a policy na mailbox do usuário.
  4. Dispara o Managed Folder Assistant manualmente (senão ele só roda no schedule da Microsoft, que é uma vez ao dia).

O servidor faz o trabalho dele em background, no seu tempo (geralmente 1-24h dependendo de carga). Em troca: sem throttle. Você não paga em rate limit porque não é a sua app que move — é o próprio Exchange.

mrm_provider.py — o coração (clique para expandir) 
def _connect_block() -> str:
    """PS snippet que conecta no Exchange Online via cert auth."""
    return f"""
Import-Module ExchangeOnlineManagement -ErrorAction Stop
$pwd = ConvertTo-SecureString -String '{settings.cert_password}' -Force -AsPlainText
Connect-ExchangeOnline `
  -AppId '{settings.client_id}' `
  -CertificateFilePath '{settings.cert_path}' `
  -CertificatePassword $pwd `
  -Organization '{settings.exo_organization}' `
  -ShowBanner:$false `
  -CommandName New-RetentionPolicyTag,Set-RetentionPolicyTag,Get-RetentionPolicyTag,
               New-RetentionPolicy,Set-RetentionPolicy,Get-RetentionPolicy,
               Set-Mailbox,Get-Mailbox,Enable-Mailbox,
               Start-ManagedFolderAssistant,
               Get-MailboxFolderStatistics,Get-MailboxStatistics,
               Get-OrganizationConfig,Set-OrganizationConfig
"""


def apply_retention(mailbox_email: str, months: int, scope: str = "all") -> MRMResult:
    """Cria/reusa tag + policy, aplica na mailbox, dispara MFA."""
    tag_name = f"VS-Archive-{months}m"
    policy_name = f"VS-MailboxCleaner-{months}m"
    age_days = months * 30

    script = f"""
# 1. Garante o tag (idempotente)
$tag = Get-RetentionPolicyTag -Identity '{tag_name}' -ErrorAction SilentlyContinue
if (-not $tag) {{
  New-RetentionPolicyTag -Name '{tag_name}' `
    -Type All `
    -RetentionAction MoveToArchive `
    -AgeLimitForRetention {age_days} `
    -RetentionEnabled $true | Out-Null
}}

# 2. Garante a policy ligada ao tag
$policy = Get-RetentionPolicy -Identity '{policy_name}' -ErrorAction SilentlyContinue
if (-not $policy) {{
  New-RetentionPolicy -Name '{policy_name}' `
    -RetentionPolicyTagLinks '{tag_name}' | Out-Null
}} else {{
  Set-RetentionPolicy -Identity '{policy_name}' `
    -RetentionPolicyTagLinks '{tag_name}' | Out-Null
}}

# 3. Garante archive habilitado + auto-expand
$mbx = Get-Mailbox -Identity '{mailbox_email}'
if ($mbx.ArchiveStatus -ne 'Active') {{
  Enable-Mailbox -Identity '{mailbox_email}' -Archive | Out-Null
}}
if (-not $mbx.AutoExpandingArchiveEnabled) {{
  Enable-Mailbox -Identity '{mailbox_email}' -AutoExpandingArchive | Out-Null
}}

# 4. Aplica a policy e desabilita RetentionHold (importante!)
Set-Mailbox -Identity '{mailbox_email}' `
  -RetentionPolicy '{policy_name}' `
  -RetentionHoldEnabled $false | Out-Null

# 5. Dispara o Managed Folder Assistant
Start-ManagedFolderAssistant -Identity '{mailbox_email}'
"""

    rc, stdout, stderr = _run_ps(script, timeout=300)
    return MRMResult(
        success=(rc == 0),
        tag_name=tag_name,
        policy_name=policy_name,
        stdout=stdout,
        stderr=stderr,
    )
Linha que custou 4 horas: RetentionHoldEnabled $false. Se a mailbox tem RetentionHold ativo (default em alguns títulos M365), o MFA não processa nada e você não tem mensagem de erro. Documentei isso como bloqueio #1 da matriz.

Auth: cert obrigatório pro Exchange PS

Microsoft Graph aceita client-secret. Exchange Online PowerShell não aceita. Só aceita certificate-based app authentication. Esse foi o segundo "perdido". Gerar o cert na primeira vez:

gerar self-signed cert + upload no App Reg (clique para expandir) 
# Em PowerShell admin
$cert = New-SelfSignedCertificate `
  -Subject "CN=MailboxCleaner-Service" `
  -CertStoreLocation "Cert:\CurrentUser\My" `
  -KeyExportPolicy Exportable `
  -KeySpec Signature `
  -KeyLength 2048 `
  -KeyAlgorithm RSA `
  -HashAlgorithm SHA256 `
  -NotAfter (Get-Date).AddYears(2)

$cert.Thumbprint  # cola em CERT_THUMBPRINT do .env

# Exportar pra cer (vai pro App Registration no Entra)
Export-Certificate -Cert $cert -FilePath ".\backend\cert.cer"

# Exportar pra pfx (vai pro Python via cert_path + cert_password)
$pwd = ConvertTo-SecureString -String "MinhaSenhaForte!" -Force -AsPlainText
Export-PfxCertificate -Cert $cert -FilePath ".\backend\cert.pfx" -Password $pwd

No Entra (Azure AD), o App Registration precisa de:

  • Office 365 Exchange Online → Exchange.ManageAsApp (Application permission, com admin consent)
  • Office 365 Exchange Online → full_access_as_app (só se você também usa EWS fallback)
  • Microsoft Graph → Reports.Read.All (pro ranking via Graph Reports API)
  • Microsoft Graph → User.Read.All (display name nos rankings)
  • Role Exchange Administrator atribuída ao service principal (pra rodar Set-Mailbox, retention, etc.)
Atribuir Exchange Administrator ao app, não ao usuário. Esse passo é em "Roles and administrators" do Entra, não em "API permissions". Pesquise pelo nome do service principal do app e atribua. Sem isso, Set-Mailbox retorna "user is not authorized" mesmo com permission API correta.

Job store em sqlite: simples e durabilidade local

Cada limpeza vira um job persistido em sqlite local. O job guarda:

  • Baseline: contagem/tamanho da caixa antes do apply.
  • Status: pending, running, completed, error.
  • Polling result: a cada 15 minutos, atualiza current_count e current_size.
retention_jobs.py — modelo sqlite (clique para expandir) 
CREATE_SQL = """
CREATE TABLE IF NOT EXISTS retention_jobs (
    id TEXT PRIMARY KEY,
    mailbox_email TEXT NOT NULL,
    months INTEGER NOT NULL,
    scope TEXT NOT NULL,
    status TEXT NOT NULL,         -- pending | running | completed | error
    baseline_count INTEGER,
    baseline_size_bytes INTEGER,
    baseline_archive_size_bytes INTEGER,
    current_count INTEGER,
    current_size_bytes INTEGER,
    current_archive_size_bytes INTEGER,
    last_poll_at TIMESTAMP,
    completed_at TIMESTAMP,
    tag_name TEXT,
    policy_name TEXT,
    error_message TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_jobs_status ON retention_jobs(status);
CREATE INDEX IF NOT EXISTS idx_jobs_mailbox ON retention_jobs(mailbox_email);
"""


def create_job(mailbox: str, months: int, scope: str) -> str:
    job_id = str(uuid.uuid4())
    baseline = capture_baseline(mailbox)
    with conn() as c:
        c.execute("""
            INSERT INTO retention_jobs
              (id, mailbox_email, months, scope, status,
               baseline_count, baseline_size_bytes, baseline_archive_size_bytes)
            VALUES (?, ?, ?, ?, 'pending', ?, ?, ?)
        """, (job_id, mailbox, months, scope,
              baseline.count, baseline.size_bytes, baseline.archive_size_bytes))
    return job_id

Background poller a cada 15 minutos

Uma thread rodando em background atualiza os jobs pendentes:

retention_poller.py — loop de polling (clique para expandir) 
import time
import threading
from .retention_jobs import list_pending, update_job
from ..providers.mrm_provider import get_mailbox_stats

POLL_INTERVAL = 15 * 60  # 15 minutos
COMPLETION_DELTA_THRESHOLD = 100  # < 100 itens novos em 30min → concluído


def _poller_loop():
    while True:
        try:
            jobs = list_pending()
            for j in jobs:
                stats = get_mailbox_stats(j.mailbox_email)
                delta_count = j.baseline_count - stats.count
                archive_delta = stats.archive_size_bytes - j.baseline_archive_size_bytes

                # Critério de "completed":
                # archive cresceu E mailbox primary parou de cair
                if archive_delta > 0 and abs(stats.count - (j.current_count or j.baseline_count)) < COMPLETION_DELTA_THRESHOLD:
                    # Marcar como completed se ficou estável por 30 min
                    if j.stable_since and (time.time() - j.stable_since) > 1800:
                        update_job(j.id, status="completed",
                                   completed_at=datetime.utcnow())
                        continue

                update_job(
                    j.id,
                    current_count=stats.count,
                    current_size_bytes=stats.size_bytes,
                    current_archive_size_bytes=stats.archive_size_bytes,
                    last_poll_at=datetime.utcnow(),
                )
        except Exception as e:
            logger.exception("poller failed")
        time.sleep(POLL_INTERVAL)


def start_poller():
    t = threading.Thread(target=_poller_loop, daemon=True)
    t.start()

Ranking de mailboxes: Graph Reports API

O ranking inicial (pra TI saber quais mailboxes atacar) vem da Microsoft Graph Reports API:

graph_reports.py — getMailboxUsageDetail (clique para expandir) 
import requests
import csv
from io import StringIO
from typing import Literal

PERIOD = Literal["D7", "D30", "D90", "D180"]


def fetch_mailbox_usage(period: PERIOD = "D7", token: str = None) -> list[dict]:
    """
    Retorna ranking de mailboxes por % de uso da quota.
    Graph Reports API devolve CSV diretamente.
    """
    url = f"https://graph.microsoft.com/v1.0/reports/getMailboxUsageDetail(period='{period}')"
    resp = requests.get(url, headers={"Authorization": f"Bearer {token}"})
    resp.raise_for_status()

    # CSV com headers: Report Refresh Date, User Principal Name, Storage Used (Byte),
    #                  Issue Warning Quota (Byte), Prohibit Send Quota (Byte), ...
    reader = csv.DictReader(StringIO(resp.text))
    rows = []
    for row in reader:
        used = int(row["Storage Used (Byte)"])
        quota = int(row["Prohibit Send Quota (Byte)"])
        rows.append({
            "upn": row["User Principal Name"],
            "used_bytes": used,
            "quota_bytes": quota,
            "percent": (used / quota * 100) if quota else 0,
            "item_count": int(row["Item Count"]),
            "last_activity": row["Last Activity Date"],
        })

    return sorted(rows, key=lambda r: r["percent"], reverse=True)
Graph Reports atualiza 1x/dia (00:00 UTC). Não é real-time. Mailbox de novo usuário só aparece no ranking dois dias depois. Pra real-time durante uma limpeza ativa, uso Get-MailboxStatistics direto via PowerShell.

"Exibir nomes ocultos" do Microsoft Admin Center

Detalhe que custou tempo: por padrão, M365 Admin Center tem configuração "Exibir nomes ocultos = OFF" em Configurações da Organização → Relatórios. Isso faz a Graph Reports retornar UPN hasheado (EBC0CB6FA63CB6D2C3D...) em vez de email real. Ligar essa configuração é o primeiro passo, senão o ranking fica inutilisável.

Matriz de bloqueios: quando MFA não move

Depois de vários casos onde apliquei retention policy e nada acontecia, montei essa matriz de verificação. Cada bloqueio tem o comando PS pra checar:

#BloqueioComo checar
1RetentionHoldEnabled=TrueGet-Mailbox X — backend força False no apply
2LitigationHoldEnabled=Truebloqueio compliance, requer ação separada
3InPlaceHolds não vazioidem
4ComplianceTagHoldApplied=Truetag de compliance, requer ação separada
5ArchiveStatus != Activebackend habilita auto via Enable-Mailbox -Archive
6Tag RetentionEnabled=FalseGet-RetentionPolicyTag
7Policy não atribuídaGet-Mailbox field RetentionPolicy
8Tag não está na policyGet-RetentionPolicy field RetentionPolicyTagLinks
9Archive cheio + AutoExpand offGet-MailboxStatistics -Archive + Get-OrganizationConfig
10Mailbox não é UserMailboxGet-Mailbox field RecipientTypeDetails
11ELC tenant disabledGet-OrganizationConfig field ElcProcessingDisabled
12Licença erradasem ExchangeOnlineArchiving ou Plan 2

Backend force (1) e (9) automaticamente. Os outros precisam de ação manual com aprovação do time legal/compliance.

Quanto tempo o MFA leva?

Microsoft documenta "até 7 dias". Observado em produção:

  • Apply → MFA começar a agir: 16-22 horas.
  • MFA processando: ~700-800 itens/hora em archive moves cross-mailbox.
  • Item count primary cai imediatamente quando MFA processa.
  • Tamanho liberado de quota: até 14 dias depois (Recoverable Items dumpster retém items deletados antes de purgar fisicamente).
"O usuário reclamou que sumiu 5GB mas a quota não caiu." Isso é o dumpster. Os e-mails Já foram pro archive, mas o slot que ocupavam no primary ainda está "reserved" por 14 dias (Recoverable Items). Quando purgar fisicamente, quota cai. Documentei isso na UI pra não ter expectativa errada.

Problemas que tive no caminho

1. EWS bulk_move com 50 itens/batch + 8 threads = throttle storm

Versão anterior do projeto era 100% EWS bulk_move. Tentei "faço batch maior + mais threads" pra acelerar. Resultado: Microsoft começou a retornar ErrorTimeoutExpired + ErrorServerBusy. Reduzi pra batch 20 + 2 threads + FaultTolerance retry. Aí descobri MRM e abandonei EWS pra cleanup em volume. EWS só sobrou pra moves manuais individuais.

2. .onmicrosoft.com obrigatório em Connect-ExchangeOnline -Organization

Tenant tem dois nomes: o verified domain (ex.: vitoriastone.com) e o onmicrosoft (ex.: vitoriastoneltda.onmicrosoft.com). Connect-ExchangeOnline EXIGE o segundo, não aceita o primeiro. Demorei pra descobrir — o erro é genérico ("organization not found").

script pra descobrir o .onmicrosoft.com (clique para expandir) 
def get_onmicrosoft_domain(token: str) -> str:
    """Busca o dominio .onmicrosoft.com do tenant via Graph."""
    resp = requests.get(
        "https://graph.microsoft.com/v1.0/domains",
        headers={"Authorization": f"Bearer {token}"},
    )
    for d in resp.json()["value"]:
        if d["id"].endswith(".onmicrosoft.com"):
            return d["id"]
    raise RuntimeError("nenhum dominio .onmicrosoft.com encontrado")

3. PT-BR locale no PowerShell quebra parsing numérico

Get-MailboxFolderStatistics em servidor com locale pt-BR retorna "FolderSize: 1.234 GB (1.234.567.890 bytes)" — pontos como separadores de milhar. Meu regex parsing inicial dava cast errado. Solução:

parser de tamanho com PT-BR awareness (clique para expandir) 
import re

def parse_bytes(s: str) -> int:
    """
    Converte 'FolderSize: 1.234 GB (1.234.567.890 bytes)' em int.
    Funciona em locale pt-BR (ponto = milhar) e en-US (vírgula = milhar).
    """
    m = re.search(r"\(([\d.,]+)\s*bytes?\)", s)
    if not m:
        return 0
    digits = re.sub(r"[,.]", "", m.group(1))
    return int(digits)

4. Enable-OrganizationCustomization é one-shot e obrigatório

Em tenant novo, antes de qualquer Set-OrganizationConfig, você tem que rodar Enable-OrganizationCustomization uma vez. Tenant antigo já tem habilitado. Se você não roda em tenant novo, qualquer Set falha com mensagem confusa. Backend roda isso na primeira execução.

5. Microsoft Graph não suporta Online Archive moves

Tentei a abordagem moderna primeiro: Graph API. Endpoint /users/{id}/messages/{id}/move com destinationId=archiveinbox retorna 404 com mensagem "Item exists in archive mailbox". A documentação não avisa que método não suporta cross-mailbox (primary → archive é cross-mailbox no modelo Exchange). Voltei pra EWS pra moves individuais, MRM pra bulk.

O que vem pela frente

  • Auth admin na UI: hoje sem auth, só localhost. Adicionar Cognito ou Entra SSO.

Conclusão

A lição: quando uma API parece impossível de escalar (EWS com throttle de 5 items/s), provavelmente existe um caminho oficial diferente que você não conhece. MRM Retention Policy é o que a própria Microsoft usa internamente pra cleanup — e é exposível via PowerShell. Sempre vale ler o que o vendor recomenda antes de brigar com a API errada.

Esse projeto não é AWS, mas a lição de engenharia é universal: troque "como eu faço A funcionar mais rápido?" por "qual o caminho oficial pra esse problema?". Geralmente o segundo caminho existe, é menos sexy (PowerShell em vez de Graph), mas resolve 10x melhor.

Se você tem caixas M365 cheias na sua empresa, esse padrão é o caminho. Implementação cabe em ~600 linhas Python + scripts PS. App Registration leva 20 minutos. ROI: zero ticket de "minha caixa travou" depois de implementado.
