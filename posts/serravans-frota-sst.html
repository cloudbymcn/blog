SaaS de gestão de frota para oficinas de vans com OCR de cupom fiscal

SaaS multi-tenant na AWS para oficinas mecânicas que prestam serviço de frota terceirizada de vans (Total Diesel como primeira cliente). Motorista faz checklist diário com 5 fotos, abastece e bate foto do cupom — Amazon Textract AnalyzeExpense lê valor e litros automaticamente. PWA Next.js 15, IaC TypeScript com SST v3, DynamoDB single-table, isolamento por tenantId no JWT do Cognito.

O contexto

Esse projeto começou de um problema bem do mundo real: oficinas mecânicas que prestam serviço de frota terceirizada (uma sai e leva 7-10 vans de cliente, faz manutenção, devolve) precisam de três coisas que planilha Excel não resolve:

  1. Conferência diária de cada veículo (5 fotos + odômetro + observações) feita por um motorista no celular, no pátio.
  2. Abastecimento rastreado: cada vez que o veículo enche tanque, motorista bate foto do cupom fiscal. Sistema lendo cupom é muito melhor que motorista digitando valor a mão.
  3. Manutenção preventiva: avisar o dono da oficina ANTES do veículo precisar — "vai bater 30 dias ou 500km, está na hora da revisão".

O nome do projeto é SerraVans. A primeira oficina usando é a Total Diesel.

Print: tela de login (motorista vs admin)
Tela inicial com dois fluxos: admin login por email/senha, ou motorista escaneia QR code do celular do administrador para entrar. assets/img/posts/serravans-login.png.

O ponto chave da arquitetura: multi-tenant desde dia 1. Uma instalação da AWS Lambda, um Cognito User Pool, mas cada oficina vê apenas a sua frota. Custo de adicionar um novo cliente: criar registro de tenant + convidar admin. Zero infra nova.

SST v3 (Ion): IaC em TypeScript

Optei por SST sobre CDK ou Terraform porque o projeto já tinha Next.js, então o stack do dev era TypeScript de qualquer jeito. SST v3 (codenome "Ion") é uma reescrita sobre Pulumi com tooling muito superior à v2 (que era CDK puro).

sst.config.ts — resources principais (clique para expandir)

export default $config({
  app(input) {
    return {
      name: "serravans",
      removal: input?.stage === "prod" ? "retain" : "remove",
      home: "aws",
      providers: { aws: { region: "us-east-1" } },
    };

  async run() {
    // ─── S3 bucket de fotos com lifecycle ──────────────────
    const photosBucket = new sst.aws.Bucket("Photos", {

      cors: {
        allowOrigins: ["*"],
        allowMethods: ["GET", "PUT", "POST"],
        allowHeaders: ["*"],
        maxAge: "1 hour",
      },
      transform: {
        bucket: (args) => {
          args.lifecycleRules = [
            {
              id: "archive-old-photos",
              enabled: true,
              transitions: [
                { days: 30, storageClass: "STANDARD_IA" },
                { days: 180, storageClass: "GLACIER_IR" },
              ],
            },
          ];
        },
      },
    });

    // ─── DynamoDB single-table com 2 GSIs ──────────────────
    const table = new sst.aws.Dynamo("Data", {
      fields: {
        pk: "string", sk: "string",
        gsi1pk: "string", gsi1sk: "string",
        gsi2pk: "string", gsi2sk: "string",
      },
      primaryIndex: { hashKey: "pk", rangeKey: "sk" },
      globalIndexes: {
        gsi1: { hashKey: "gsi1pk", rangeKey: "gsi1sk" },
        gsi2: { hashKey: "gsi2pk", rangeKey: "gsi2sk" },
      },
      transform: {
        table: (args) => {
          args.pointInTimeRecovery = { enabled: true };
        },
      },
    });

    // ─── Cognito com custom attributes ─────────────────────
    const userPool = new sst.aws.CognitoUserPool("Users", {
      usernames: ["email"],
      transform: {
        userPool: {
          schemas: [
            {
              name: "tenantId",
              attributeDataType: "String",
              mutable: true,
              stringAttributeConstraints: { minLength: "1", maxLength: "64" },
            },
            {
              name: "role",
              attributeDataType: "String",
              mutable: true,
              stringAttributeConstraints: { minLength: "1", maxLength: "16" },
            },
          ],
          passwordPolicy: {
            minimumLength: 10,
            requireLowercase: true,
            requireNumbers: true,
            requireUppercase: true,
          },
        },
      },
    });

    // ─── Location Service ──────────────────────────────────
    const placeIndex = new aws.location.PlaceIndex("Places", {

Multi-tenant: tenantId em tudo

A peça mais importante do design. O tenantId é um atributo custom do Cognito injetado no JWT. Toda consulta no DynamoDB tem ele como prefixo da PK, isolando os tenants por design.

middleware de auth + tenant (clique para expandir) 
// apps/api/src/lib/auth.ts
import { jwtVerify, createRemoteJWKSet } from "jose";

const JWKS = createRemoteJWKSet(
  new URL(`https://cognito-idp.us-east-1.amazonaws.com/${process.env.USER_POOL_ID}/.well-known/jwks.json`)
);

export interface UserContext {
  userId: string;
  email: string;
  tenantId: string;
  role: "admin" | "driver";
}

export async function authenticate(event: APIGatewayProxyEventV2): Promise<UserContext> {
  const token = event.headers.authorization?.replace("Bearer ", "");
  if (!token) throw new HttpError(401, "missing token");

  const { payload } = await jwtVerify(token, JWKS, {
    issuer: `https://cognito-idp.us-east-1.amazonaws.com/${process.env.USER_POOL_ID}`,
    audience: process.env.USER_POOL_CLIENT_ID,
  });

  const tenantId = payload["custom:tenantId"] as string;
  const role = payload["custom:role"] as string;
  if (!tenantId) throw new HttpError(403, "user without tenant");

  return {
    userId: payload.sub!,
    email: payload.email as string,
    tenantId,
    role: role as "admin" | "driver",
  };
}

Como toda PK começa com TENANT#, queries do tenant batem na mesma partition, fica super-rápido e barato.

GSI1 e GSI2: respondendo perguntas inversas

  • GSI1 (gsi1pk-gsi1sk): invertido por entidade. Ex: ver tudo de uma placa específica entre vários tenants — não vai acontecer no app de cliente, mas no admin global do SaaS sim.
  • GSI2 (gsi2pk-gsi2sk): ordenado por data global. Ex: "últimos abastecimentos de hoje em todos os tenants" pra debugging.

OCR de cupom fiscal: Amazon Textract

Esse foi o "wow" do projeto. Motorista enche tanque, bate uma foto do cupom no balcão do posto, sistema lê valor pago e litros automaticamente. Tempo entre foto e form preenchido: ~3 segundos.

Usei o AnalyzeExpense do Textract, que é específico pra cupons/notas:

apps/api/src/routes/ocr.ts — OCR de cupom (clique para expandir) 
import { TextractClient, AnalyzeExpenseCommand } from "@aws-sdk/client-textract";

const textract = new TextractClient({});

interface CupomResult {
  total: number | null;
  litros: number | null;
  data: string | null;
  posto: string | null;
  confidence: number;
}

export async function analyzeCupom(bucket: string, key: string): Promise<CupomResult> {
  const resp = await textract.send(new AnalyzeExpenseCommand({
    Document: {
      S3Object: { Bucket: bucket, Name: key },
    },
  }));

  const fields = resp.ExpenseDocuments?.[0]?.SummaryFields ?? [];
  const lineItems = resp.ExpenseDocuments?.[0]?.LineItemGroups?.[0]?.LineItems ?? [];

  // 1. Total pago: campo "TOTAL"
  const totalField = fields.find((f) =>
    f.Type?.Text === "TOTAL" || f.Type?.Text === "AMOUNT_PAID"
  );
  const total = parseBrazilCurrency(totalField?.ValueDetection?.Text);

  // 2. Litros: heurística nos line items (procura "L" ou "Litros")
  let litros: number | null = null;
  for (const item of lineItems) {
    for (const f of item.LineItemExpenseFields ?? []) {
      const txt = f.ValueDetection?.Text ?? "";
      const match = txt.match(/(\d+[.,]?\d*)\s*L(itros)?$/i);
      if (match) {
        litros = parseFloat(match[1].replace(",", "."));
        break;
      }
    }
    if (litros) break;
  }

  // 3. Data: campo INVOICE_RECEIPT_DATE
  const dataField = fields.find((f) => f.Type?.Text === "INVOICE_RECEIPT_DATE");
  const data = dataField?.ValueDetection?.Text ?? null;

  // 4. Nome do posto: VENDOR_NAME
  const postoField = fields.find((f) => f.Type?.Text === "VENDOR_NAME");
  const posto = postoField?.ValueDetection?.Text ?? null;

  // 5. Confiança média dos campos lidos
  const conf = [totalField, dataField, postoField]
    .map((f) => f?.ValueDetection?.Confidence ?? 0)
    .filter((c) => c > 0);
  const confidence = conf.length ? conf.reduce((a, b) => a + b, 0) / conf.length : 0;

  return { total, litros, data, posto, confidence };
}

function parseBrazilCurrency(s?: string): number | null {
  if (!s) return null;
  // "R$ 312,45" → 312.45
  const clean = s.replace(/[^\d,.-]/g, "").replace(/\./g, "").replace(",", ".");
  const n = parseFloat(clean);
  return isNaN(n) ? null : n;
}
Por que AnalyzeExpense e não DetectDocumentText + regex? AnalyzeExpense já tem o modelo treinado pra entender "TOTAL" / "VENDOR" / "DATE" mesmo em cupons brasileiros. Custa ~$0.01 por página vs $0.0015 do DetectDocumentText, mas a qualidade do parse é muito superior. Para 200 cupons/mês, fica $2.

Fluxo completo: foto → OCR → form pré-preenchido

fluxo completo (clique para expandir) 
// apps/api/src/routes/fuelings.ts (POST /fuelings/parse-receipt)

export async function parseReceipt(event: APIGatewayProxyEventV2) {
  const user = await authenticate(event);
  const { uploadKey } = JSON.parse(event.body ?? "{}");

  // Valida que o usuário dono do tenant subiu esse upload
  if (!uploadKey.startsWith(`tenants/${user.tenantId}/uploads/`)) {
    throw new HttpError(403, "upload alheio");
  }

  // 1. OCR via Textract
  const cupom = await analyzeCupom(process.env.PHOTOS_BUCKET!, uploadKey);

  // 2. Se confiança baixa, marca pra revisão humana
  const needsReview = cupom.confidence < 80;

  return {
    statusCode: 200,
    body: JSON.stringify({
      ...cupom,
      needsReview,
      pre_filled: !needsReview,
    }),
  };
}
Confiança < 80% força a UI a mostrar warning amarelo. Motorista vê "confirme valores", deve digitar ou corrigir. Sem isso, OCR ruim virava abastecimento de R$ 0,00 ou 312 litros (em vez de 31,2).

Checklist diário: 5 fotos + odômetro

Quando o motorista entra no veículo de manhã, ele faz um checklist obrigatório antes de poder dirigir:

  1. Foto da frente
  2. Foto da traseira
  3. Foto da lateral direita
  4. Foto da lateral esquerda
  5. Foto do odômetro (com leitura confirmada)

Cada foto é uploaded via Presigned URL direto pro S3, sem passar pelo Lambda. O Lambda apenas registra o checkin no DynamoDB após os 5 uploads.

presigned upload sequence (clique para expandir) 
// POST /uploads/presign
export async function presignUpload(event: APIGatewayProxyEventV2) {
  const user = await authenticate(event);
  const { kind, fileName, contentType } = JSON.parse(event.body ?? "{}");
  // kind = "checkin" | "fueling" | "maintenance"

  const key = `tenants/${user.tenantId}/uploads/${kind}/${randomUUID()}-${fileName}`;

  const cmd = new PutObjectCommand({
    Bucket: process.env.PHOTOS_BUCKET,
    Key: key,
    ContentType: contentType,
    Metadata: {
      uploaded_by: user.userId,
      tenant: user.tenantId,
    },
  });

  const url = await getSignedUrl(s3, cmd, { expiresIn: 300 });
  return { statusCode: 200, body: JSON.stringify({ url, key }) };
}
Sempre prefixe upload key com tenants/<id>/. Esse é o gate principal de isolamento multi-tenant. Em qualquer rota que lê do bucket, valido que a key começa com o tenant do usuário. Sem isso, um tenant maliciosamente bem informado conseguiria pedir Presigned URL pra ler upload de outro tenant.

Geocoding com Amazon Location Service

Quando motorista termina o expediente, marca "encerrar dia" e o sistema captura latitude/longitude do navegador. Eu uso Location Service pra transformar coordenada em endereço legível (geocoding reverso), que vai no relatório.

apps/api/src/lib/geo.ts — reverse geocoding (clique para expandir) 
import { LocationClient, SearchPlaceIndexForPositionCommand }
  from "@aws-sdk/client-location";

const loc = new LocationClient({});

export async function reverseGeocode(lat: number, lng: number): Promise<string> {
  const resp = await loc.send(new SearchPlaceIndexForPositionCommand({
    IndexName: process.env.PLACE_INDEX_NAME,
    Position: [lng, lat],     // [longitude, latitude]
    MaxResults: 1,
  }));

  const place = resp.Results?.[0]?.Place;
  if (!place) return `${lat.toFixed(5)}, ${lng.toFixed(5)}`;

  // Monta endereço curto
  const parts = [
    place.AddressNumber && place.Street ? `${place.Street}, ${place.AddressNumber}` : place.Street,
    place.Municipality,
    place.Region,
  ].filter(Boolean);

  return parts.join(" · ");
}
Esri (data source) e SingleUse. O Place Index foi configurado com intendedUse: "SingleUse", não "Storage". Diferença de licença: SingleUse pode ser usado em apps end-user de mapa interativo, mas não persistido. Eu não salvo a string do endereço — salvo apenas lat/lng e faço reverse on-demand. Fica legal com o termo Esri.

Toda manhã (10h BRT = 13h UTC), uma Lambda separada roda pra avisar admins sobre veículos chegando perto da manutenção:

maintenance-check.ts — lógica do alerta (clique para expandir) 
// Lê todos os veículos de todos os tenants
// Para cada um, calcula:
//   - dias desde última manutenção
//   - km percorridos desde última manutenção
// Se atingiu 80% do limite (30 dias ou 500km), entra na lista de alerta.

export async function handler() {
  const allVehicles = await scanAllVehicles();   // single scan, ~hundreds

  // Agrupa por tenant pra enviar 1 email por oficina
  const alertsByTenant = new Map<string, Vehicle[]>();

  for (const v of allVehicles) {
    const lastMaint = await getLastMaintenance(v.tenantId, v.plate);
    if (!lastMaint) continue;

    const daysSince = (Date.now() - lastMaint.ts) / 86400000;
    const kmSince = v.odometer - lastMaint.odometer;

    if (daysSince >= 24 || kmSince >= 400) {  // 80% de 30d / 500km
      if (!alertsByTenant.has(v.tenantId)) alertsByTenant.set(v.tenantId, []);
      alertsByTenant.get(v.tenantId)!.push({
        ...v,
        daysSince: Math.floor(daysSince),
        kmSince,
      });
    }
  }

  // Envia email pra cada tenant
  for (const [tenantId, alerts] of alertsByTenant) {
    const tenant = await getTenant(tenantId);
    if (!tenant.alertEmail) continue;

    await ses.send(new SendEmailCommand({
      Source: process.env.SES_FROM,
      Destination: { ToAddresses: [tenant.alertEmail] },
      Message: {
        Subject: { Data: `${alerts.length} veículo(s) precisam de manutenção` },
        Body: { Html: { Data: renderAlertHtml(alerts) } },
      },
    }));
  }
}

Quando um motorista escreve uma observação no app ("freio fazendo barulho ao parar, principalmente em descida"), o admin vê no painel. Mas são dezenas de observações por dia, e o admin precisa priorizar.

Quando vale usar Bedrock vs só classificar? Pra 5-10 observações/dia, o admin lê tudo. Pra 50+, ele começa a pular — e justo aí perde o crítico. Resumir com LLM é barato ($0.005 por chamada) e devolve cog. carga gerencial.

S3 lifecycle: ~70% de economia em fotos antigas

Cada checkin tem 5 fotos de ~3MB. Em 30 dias o bucket cresceu ~50GB. Defini lifecycle agressiva:

IdadeStorage classCusto $/GB-mês
0-30 diasSTANDARD$0.023
30-180 diasSTANDARD_IA$0.0125
180+ diasGLACIER_IR$0.004

GLACIER_IR (Glacier Instant Retrieval) restaura em milissegundos — importante porque admin às vezes precisa ver foto antiga sem espera. Só o storage é mais barato.

Cuidado com versionamento + lifecycle. Habilitei versionamento no bucket. Sem lifecycle separada pras versões antigas, elas ficam em STANDARD pra sempre. Adicionei rule: noncurrent_version_transition 7 dias → GLACIER_IR, 30 dias → delete. Pra fotos de cupom fiscal isso não tem problema legal (não é documento fiscal nosso, é do posto).

Problemas que tive em produção

1. Textract latency em foto grande

Cupom fotografado em 4K (12MB) levava 8-12s no Textract. Comprimir no cliente antes de upload (canvas redimensionado para 1920px de largura) reduziu pra ~2s. Trade-off: 1% dos cupons ficavam ilegíveis. Para esses casos, motorista clica "tirar foto melhor".

2. iOS PWA + Safari + Cognito refresh token

iOS Safari deleta IndexedDB e cookies da PWA se "não usar por 7 dias". Motorista voltava da segunda passou semana, login expirava. Solução: persistir refreshToken em navigator.credentials (Credential Management API) quando disponível. Funciona em Android; iOS ainda esquece. Aceitei o trade-off (login manual a cada 7 dias inativos é aceitável).

3. Cognito Admin API throttle

Convidar 20 motoristas de uma vez via AdminCreateUser batia em throttle (~5 req/s). Adicionei delay de 250ms entre chamadas. Pra batches maiores, considerar SQS pra enfileirar.

4. Multi-tenant CORS no S3

Bucket de fotos com allowOrigins: ["*"] é muito permissivo. Mudei pra lista explícita dos domínios dos tenants. Quando alguém da Total Diesel subiu sob domínio próprio, tive que adicionar entrada. Solução longa: gerar CORS dinâmico via Lambda@Edge baseado em tabela DynamoDB.

5. Bedrock cross-region inference profile + LinkedIn API

Não relacionado, mas serviu de lição: tentei chamar Bedrock de uma Lambda que estava com Reserved Concurrency = 1. Cold start + retry exponencial = 30s. Removi reserved concurrency, tudo normalizou.

Conclusão

O que destrava esse stack pra produto comercial pequeno: SST v3 reduz IaC de centenas de linhas Terraform pra TypeScript legível; Textract resolve OCR sem treinar modelo; DynamoDB single-table com 2 GSIs é suficiente pra 95% das queries; Cognito com custom attributes faz multi-tenant sem custo extra. Pra um time pequeno construindo SaaS B2B, vale demais.

O próximo passo é abrir como produto para outras oficinas. A multi-tenancia já está pronta — o que falta é landing page, billing (Stripe ou AWS Marketplace), e onboarding self-service. Cada nova oficina é zero infra, só um registro novo na tabela.

Se você está pensando em construir SaaS pequeno na AWS sem time grande, esse modelo SST + Lambda + DynamoDB single-table + Cognito multi-tenant é o caminho mais barato pra chegar em produto vendi-vel.
