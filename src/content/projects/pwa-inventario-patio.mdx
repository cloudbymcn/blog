## O problema dos dois PowerApps

A empresa tinha dois aplicativos PowerApps em produção, cada um resolvendo metade de um mesmo problema:

-   **InventariaAI**: bipagem de chapas durante o inventário anual. Operador escaneia QR ou digita código, sistema marca como "conferido" no ERP.
-   **LocalizaAI**: inventário contínuo. Quando uma chapa mudava de pátio/cavalete, alguem precisava registrar a movimentação.

Os dois apps tinham o mesmo conjunto de problemas:

1.  **Sem offline.** O pátio das pedras é uma serraria enorme com WiFi instavel. Cair internet no meio de bipar 200 chapas significava perder bipagens, ou bipar tudo de novo.
2.  **Latência ruim.** Cada bipagem fazia uma chamada síncrona pro Dataverse, que falava com o ERP via connector custom. Tempo médio entre "bip" e "confirmado": 2-4 segundos. Pra bipar 200 chapas, 10-15 minutos úteis perdidos.
3.  **Licença.** 25 usuários × PowerApps Per User = ~R$ 1.500/mês.
4.  **UI lenta de iterar.** Editor PowerApps não tem version control, não tem diff, mudar um campo é clicar em 8 abas.

Decidi reescrever as duas em **uma só PWA serverless**, com offline de verdade e integração direta com o ERP.

## DynamoDB: 4 tabelas e os GSIs que importam

Modelei evitando o single-table extremo. O motivo: as quatro entidades têm vidas independentes, e o time técnico que vai dar manutenção vai entender melhor 4 tabelas claras do que uma com 12 prefixos.

| Tabela | PK | SK | GSIs |
| --- | --- | --- | --- |
| `patio-chapas` | CHAPA\_ID | — | ref\_vs-index, filial-localizacao-index, barcode-index |
| `patio-inventory-events` | INVENTORY\_ID | CHAPA\_ID | scanned\_by-index |
| `patio-snapshots` | INVENTORY\_ID | CHAPA\_ID | — |
| `patio-move-history` | CHAPA\_ID | TIMESTAMP | — |

Os GSIs respondem a perguntas operacionais específicas:

-   **ref\_vs-index**: "me dá todas as chapas do bloco BL-58731" (referência é mais usada que CHAPA\_ID).
-   **filial-localizacao-index**: "me lista o inventário do pátio G3 da filial matriz".
-   **barcode-index**: lookup quando o operador escaneia código de barras (não é CHAPA\_ID).
-   **scanned\_by-index**: pra ranking de produtividade.

## Offline-first: IndexedDB + flush em batch

O núcleo do app. Quando o operador bipa, a chapa _vai pro IndexedDB_ antes de qualquer chamada de rede. Se a rede está boa, o flush acontece imediatamente. Se cair, fica pendente até voltar.

<details>
<summary>frontend/src/lib/offlineQueue.js — fila no IndexedDB (clique para expandir)</summary>

```javascript
import { openDB } from "idb";
import { postScanBatch } from "./api";

const DB_NAME = "patio";
const STORE = "scan_queue";

function getDb() {
  return openDB(DB_NAME, 1, {
    upgrade(db) {
      if (!db.objectStoreNames.contains(STORE)) {
        db.createObjectStore(STORE, { keyPath: "id", autoIncrement: true });
      }
    },
  });
}

/** Grava bipagem na fila offline. */
export async function enqueue(scan) {
  const db = await getDb();
  await db.add(STORE, { ...scan, status: "pending", ts: Date.now() });
}

const BATCH_SIZE = 50;

/** Tenta enviar pendentes em batches de 50. */
export async function flush(inventoryId) {
  const db = await getDb();
  const all = await db.getAll(STORE);
  const pending = all.filter((s) => s.status === "pending");
  if (!pending.length) return { sent: 0 };

  let totalSent = 0;

  // Chunks de 50 (limite da API Gateway payload + Lambda timeout)
  for (let i = 0; i < pending.length; i += BATCH_SIZE) {
    const chunk = pending.slice(i, i + BATCH_SIZE);
    const scans = chunk.map((s) => ({
      chapa_id: s.chapa_id,
      estiva: s.estiva,
      filial: s.filial,
    }));

    try {
      const resp = await postScanBatch(inventoryId, scans);
      // Marca cada um como sent ou error baseado no retorno
      for (let k = 0; k < chunk.length; k++) {
        const result = resp.results[k];
        await db.put(STORE, {
          ...chunk[k],
          status: result.status === "ok" ? "sent" : "error",
          detail: result.detail,
        });
      }
      totalSent += resp.results.filter((r) => r.status === "ok").length;
    } catch (err) {
      // Falha no batch inteiro: deixa pendente, tenta no próximo flush
      console.error("flush batch failed:", err);
      break;
    }
  }

  return { sent: totalSent };
}
```

</details>

A UI mostra contador de pendentes no canto da tela. Cair internet é um detalhe visível, não uma falha crítica.

### Lambda scan: batch otimizado

Do lado do servidor, o handler de batch escreve no DynamoDB _também_ em batch (`batch_writer`), e enriquece os dados com `batch_get_item` em pacotes de 100:

<details>
<summary>lambda/scan/handler.py — batch_scan (clique para expandir)</summary>

```python
def handle_batch_scan(body, user_id, user_name):
    """POST /scan/batch — offline sync batch (otimizado com batch_get)."""
    inventory_id = body["inventory_id"]
    scans = body["scans"]
    now = datetime.now(timezone.utc).isoformat()

    # 1. Enriquecer chapas via batch_get (resource API, até 100 keys por chamada)
    chapa_ids = list({s["chapa_id"] for s in scans})
    chapas_map = {}
    for i in range(0, len(chapa_ids), 100):
        batch_keys = [{"CHAPA_ID": cid} for cid in chapa_ids[i:i+100]]
        resp = dynamodb.batch_get_item(
            RequestItems={chapas_table.name: {"Keys": batch_keys}}
        )
        for item in resp.get("Responses", {}).get(chapas_table.name, []):
            chapas_map[item["CHAPA_ID"]] = item

    # 2. Write events em batch (batch_writer agrupa de 25 em 25)
    results = []
    with events_table.batch_writer() as batch:
        for scan in scans:
            chapa_id = scan["chapa_id"]
            chapa = chapas_map.get(chapa_id)
            if not chapa:
                results.append({"chapa_id": chapa_id, "status": "error",
                                "detail": {"error": "não encontrada"}})
                continue
            try:
                batch.put_item(Item={
                    "INVENTORY_ID": inventory_id,
                    "CHAPA_ID": chapa_id,
                    "ref_bloco": chapa.get("ref_bloco", ""),
                    "scanned_by": user_id,
                    "scanned_by_name": user_name,
                    "scanned_at": now,
                    "estiva_encontrada": scan["estiva"],
                    "filial": scan["filial"],
                    "material": chapa.get("material", ""),
                    "synced_to_firebird": False,
                })
                results.append({"chapa_id": chapa_id, "status": "ok"})
            except Exception as e:
                results.append({"chapa_id": chapa_id, "status": "error",
                                "detail": {"error": str(e)}})
    return response(200, {"results": results})
```

</details>

<Callout type="info">

**Sem `batch_writer`, escrever 50 itens custa 50 PutItem.** Com `batch_writer`, custa 2 BatchWriteItem (DynamoDB aceita 25 por batch). Latência cai de ~2.5s pra ~200ms.

</Callout>

### Conditional write contra duplicado

No bipagem individual (`POST /scan`), uso `ConditionExpression` pra impedir duplicada:

<details>
<summary>scan single — condicional (clique para expandir)</summary>

```python
try:
    events_table.put_item(
        Item={...},
        ConditionExpression="attribute_not_exists(INVENTORY_ID) AND attribute_not_exists(CHAPA_ID)",
    )
except dynamodb.meta.client.exceptions.ConditionalCheckFailedException:
    return response(409, {"error": "Chapa já bipada neste inventário", "chapa_id": chapa_id})
```

</details>

No batch eu não uso condicional — `batch_writer` não aceita `ConditionExpression`. Aceito o overwrite porque o offline pode reenviar uma bipagem várias vezes, mas o item é idempotente (mesma chapa, mesmo inventory, sobrescreve com mesmo conteúdo).

## DynamoDB Streams: sync de volta no Firebird

O sistema legado (ERP legado, Firebird) precisa enxergar as bipagens em real time. Não dá pra trocar o ERP, mas dá pra escrever de volta. Solução: DynamoDB Streams → Lambda dentro da VPC → UPDATE Firebird.

<details>
<summary>lambda/firebird_sync/handler.py — conexão Firebird (clique para expandir)</summary>

```python
import json
import os
import boto3
import fdb   # driver Firebird

SYNC_ENABLED = os.environ.get("SYNC_ENABLED", "false").lower() == "true"
FIREBIRD_SECRET_ARN = os.environ.get("FIREBIRD_SECRET_ARN", "")

_fb_creds = None

def get_firebird_creds():
    """Busca credenciais Firebird do Secrets Manager (cache módulo)."""
    global _fb_creds
    if _fb_creds:
        return _fb_creds
    client = boto3.client("secretsmanager")
    resp = client.get_secret_value(SecretId=FIREBIRD_SECRET_ARN)
    _fb_creds = json.loads(resp["SecretString"])
    return _fb_creds

def get_firebird_conn():
    creds = get_firebird_creds()
    return fdb.connect(
        host=creds["host"],
        port=int(creds.get("port", 3050)),
        database=creds["database"],
        user=creds["username"],
        password=creds["password"],
        charset="UTF8",
    )

UPDATE_SQL = """
    UPDATE TABBLOCOCHAPAS
    SET CONFERIDO = 1,
        DATAHORACONFERENCIA = ?,
        USUARIOCONFERENCIA = ?,
        CODIGOLOCALIZACAO = ?
    WHERE CODIGOBLOCO = ?
      AND CODIGO = ?
"""

def lambda_handler(event, context):
    """DynamoDB Streams → Firebird sync."""
    if not SYNC_ENABLED:
        print("SYNC_ENABLED=false, skipping")
        return {"processed": 0, "skipped": len(event["Records"])}

    processed = 0
    conn = None
    try:
        for record in event["Records"]:
            if record["eventName"] != "INSERT":
                continue
            new_image = record["dynamodb"]["NewImage"]
            # Deserializar do formato Stream...
            chapa_id = new_image["CHAPA_ID"]["S"]
            scanned_at = new_image["scanned_at"]["S"]
            scanned_by = new_image["scanned_by_name"]["S"]
            estiva = new_image["estiva_encontrada"]["S"]

            # Conexão lazy
            if conn is None:
                conn = get_firebird_conn()

            cur = conn.cursor()
            cur.execute(UPDATE_SQL, (scanned_at, scanned_by, estiva, *chapa_id.split("-")))
            conn.commit()
            processed += 1
    finally:
        if conn:
            conn.close()
    return {"processed": processed}
```

</details>

### VPC, driver fdb e cold start

Essa Lambda _tem_ que rodar dentro da VPC (a EC2 Firebird está em subnet privada). VPC Lambda paga o preço de ~500ms de cold start na primeira chamada (ENI Hyperplane). Para sync de bipagem, isso não é problema crítico, pois é assíncrono (Stream).

O driver `fdb` tem uma dependência binária nativa: `libfbclient.so`. Empacotei como **Lambda Layer**:

### Feature flag SYNC\_ENABLED=false

<Callout type="danger">

**Por que SYNC\_ENABLED=false por default?** Esse era o tipo de Lambda perigoso: errar uma vez escrevia coisa errada no ERP. Durante desenvolvimento, o sync ficou desligado e eu validava a Lambda lendo CloudWatch Logs, não escrevendo no Firebird. Só depois de 2 semanas com o evento simulado em produção sem escrita é que liguei `SYNC_ENABLED=true`. Toda integração que escreve em sistema legado deveria ter esse switch.

</Callout>

## Cognito: auth + filial + grupo

Cada usuário pertence a uma filial (atributo custom `custom:filial`) e a um grupo (`operador` ou `gestores`). Os handlers Lambda checam isso direto do JWT:

<details>
<summary>auth via JWT claims (clique para expandir)</summary>

```python
def get_user_context(event):
    """Extrai claims do token Cognito (já validado pelo authorizer)."""
    claims = event["requestContext"]["authorizer"]["claims"]
    return {
        "user_id": claims["sub"],
        "user_name": claims.get("name") or claims["cognito:username"],
        "email": claims["email"],
        "filial": claims.get("custom:filial", ""),
        "groups": claims.get("cognito:groups", "").split(","),
    }

def require_gestor(event):
    """Helper: aborta se não é gestor."""
    ctx = get_user_context(event)
    if "gestores" not in ctx["groups"]:
        return None, response(403, {"error": "Apenas gestores"})
    return ctx, None
```

</details>

<Callout type="info">

**Por que filial no token e não no DynamoDB?** Cada query de bipagem precisa filtrar por filial pra não vazar dados entre unidades. Se a filial estiver em DynamoDB, é um GetItem extra a cada request. No JWT, é gratuito. Custo: trocar filial exige re-login.

</Callout>

## Export Excel/PDF: presigned S3

Gestores precisam de relatórios. Excel via `openpyxl`, PDF via `reportlab` — ambos como Layer separada (binarios pesados, ~30MB). O export não devolve o arquivo direto na resposta da API — isso quebraria limite de payload da API Gateway (6MB).

<details>
<summary>fluxo de export com presigned URL (clique para expandir)</summary>

```python
import boto3
from openpyxl import Workbook
import io
import uuid

s3 = boto3.client("s3")
EXPORTS_BUCKET = os.environ["EXPORTS_BUCKET"]

def lambda_handler(event, context):
    inventory_id = event["pathParameters"]["id"]
    format = event["queryStringParameters"].get("format", "xlsx")

    # 1. Gera o arquivo em memória
    if format == "xlsx":
        buf = generate_excel(inventory_id)
        ct = "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet"
        ext = "xlsx"
    else:
        buf = generate_pdf(inventory_id)
        ct = "application/pdf"
        ext = "pdf"

    # 2. Sobe pro S3 com TTL curto via lifecycle
    key = f"exports/{uuid.uuid4()}.{ext}"
    s3.put_object(
        Bucket=EXPORTS_BUCKET,
        Key=key,
        Body=buf.getvalue(),
        ContentType=ct,
        ContentDisposition=f'attachment; filename="inventario-{inventory_id}.{ext}"',
    )

    # 3. Devolve presigned URL de download (10 min)
    url = s3.generate_presigned_url(
        "get_object",
        Params={"Bucket": EXPORTS_BUCKET, "Key": key},
        ExpiresIn=600,
    )
    return response(200, {"url": url, "filename": f"inventario-{inventory_id}.{ext}"})
```

</details>

O bucket de exports tem _lifecycle rule_: arquivos são deletados depois de 24h. Sem isso, o bucket vira lixeira eterna.

## Reconciliação: o diff visual

No final de cada inventário, o gestor precisa saber: o que estava esperado (snapshot ERP no início), o que foi bipado (eventos), o que está faltando. Eu faço esse diff em uma Lambda dedicada:

<details>
<summary>lambda/reconcile/handler.py — diff snapshot vs eventos (clique para expandir)</summary>

```python
def reconcile(inventory_id):
    """
    Compara snapshot (expectativa) vs events (realidade).
    Retorna 4 grupos: corretas, movidas, não encontradas, novas.
    """
    snapshot = query_all(snapshots_table, "INVENTORY_ID", inventory_id)
    events = query_all(events_table, "INVENTORY_ID", inventory_id)

    snap_map = {s["CHAPA_ID"]: s for s in snapshot}
    ev_map = {e["CHAPA_ID"]: e for e in events}

    corretas = []     # estava no snap E foi bipada na mesma estiva
    movidas = []      # estava no snap E foi bipada em estiva diferente
    nao_encontradas = []  # estava no snap, não foi bipada
    novas = []        # não estava no snap, foi bipada

    for chapa_id, snap in snap_map.items():
        ev = ev_map.get(chapa_id)
        if not ev:
            nao_encontradas.append(snap)
        elif ev["estiva_encontrada"] == snap.get("estiva_esperada"):
            corretas.append(ev)
        else:
            movidas.append({**ev, "estiva_esperada": snap.get("estiva_esperada")})

    for chapa_id, ev in ev_map.items():
        if chapa_id not in snap_map:
            novas.append(ev)

    return {
        "corretas": corretas,
        "movidas": movidas,
        "nao_encontradas": nao_encontradas,
        "novas": novas,
    }
```

</details>

O frontend renderiza isso como 4 abas coloridas, cada uma com a lista exportavel. Em inventário clássico, esse passo levava dias e era feito em Excel. Agora é um GET de ~3 segundos.

```javascript
            // API: NetworkFirst com fallback de cache (5min)
            urlPattern: ({ url }) => url.pathname.startsWith("/api"),
            handler: "NetworkFirst",
            options: {
              cacheName: "api-cache",
              networkTimeoutSeconds: 3,
              expiration: { maxEntries: 100, maxAgeSeconds: 300 },
            },
          },
          {
            // Assets: CacheFirst com hash
            urlPattern: /\.(?:js|css|woff2)$/,
            handler: "CacheFirst",
            options: {
              cacheName: "assets-cache",
              expiration: { maxEntries: 60, maxAgeSeconds: 7 * 24 * 60 * 60 },
            },
          },
        ],
      },
    }),
  ],
});
```

## Três modos de scan, um cenário real

A primeira versão tinha só "scanner de câmera" pra ler QR code. Em campo, descobri que:

1.  QR sujo de pó de pedra não lê.
2.  Chapa em pé com sol direto fica espelhada, câmera não foca.
3.  Operador com luva não consegue manter câmera firme.

Solução: três modos co-existindo, o operador escolhe:

-   **Modo Rápido**: keypad grande de números + botões de cor (vermelho/verde/azul/amarelo/...). Operador "digita" estiva + número. É o mais usado.
-   **Modo Scanner**: câmera lendo barcode/QR. Usado quando o código está legível.
-   **Modo Cores**: fallback total. Quando QR e número ilegíveis, operador clica em cores que descrevem a chapa (cor do pó, marcação no canto, etc). Match é por similaridade no DynamoDB.

<Callout type="warn">

**Sempre desenhe pro _pior_ cenário.** Eu desenhei pro melhor (QR + WiFi bom + operador focado) e o app quebrou no primeiro inventário. Quando voltei pro design, troquei a pergunta: "como funciona com operador cansado, celular barato, internet ruim, código sujo?". Aí o modo Rápido + offline-first ficou óbvio.

</Callout>

## Problemas que tive em produção

### 1\. Firebird charset UTF8 vs ANSI

O Firebird do ERP estava configurado com charset `WIN1252`. Meu driver tentava UTF-8 e dava erro silencioso em texto com acentos (nome com "ç" virava lixo). Mudei pra `WIN1252` na conexão e fiz `str.encode("cp1252")` nos campos de texto antes do UPDATE.

### 2\. Cognito email com link expira em 7 dias

Convite de novo operador (admin envia email do Cognito) tinha link de "definir senha" válido por 7 dias. Em inventário de fim de ano, eu cadastrava em novembro pra trabalhar em janeiro — link expirava. Aumentei o `TemporaryPasswordValidityDays` pra 30.

### 3\. iOS Safari + IndexedDB

iOS deleta IndexedDB de PWA se o usuário "não abre por 7 dias". Operador que volta de férias perdia toda a fila offline. Mitigação: sync ANTES de qualquer acção nova (na entrada da tela Scan, flush automático). Se a fila sumir, ele perde max as bipagens do último flush, não tudo.

### 4\. PWA install não aparecia em Android Chrome 14

Faltava o `start_url` com `?utm_source=pwa` no manifest, faltava o icone 512×512 marcado como `any maskable`, e faltava service worker registrado _antes_ do beforeinstallprompt event. Corrigir os três detalhes destravou o "Install App".

### 5\. API Gateway CORS preflight cacheou OPTIONS errado

Inicialmente `OPTIONS` retornava `Access-Control-Max-Age: 86400` sem o header `Authorization`. Browser cacheou e novos requests com Authorization eram bloqueados. Mudei o handler do OPTIONS pra retornar o pre-flight correto e baixei MaxAge pra 300s durante debug, depois subi de volta.

## Conclusão

<Callout type="success">

**A lição:** low-code (PowerApps, Retool, Bubble) é bom pra protótipo. Em produção real com requisitos reais (offline, multi-perfil, integração profunda com legacy), o custo de manutenção vira mais alto que custom code. Em 2 meses a PWA pagou todo o investimento em licença PowerApps que a empresa já tinha desembolsado.

</Callout>

Pra quem está pensando em algo parecido (substituir PowerApps/Retool em operação que precisa de offline e legacy integration): o stack PWA + Lambda + DynamoDB Streams resolve a maior parte. As pegadas são no detalhe operacional (charset Firebird, cámera no campo, iOS Safari quirks). Vale construir.

Próximos passos: migrar o Firebird sync de fdb Python pra um adapter mais robusto, talvez Java + JDBC, pra reduzir dependencias binárias. E adicionar telemetria ao frontend (Sentry ou OpenTelemetry) pra catch erros do browser que não aparecem no CloudWatch.
