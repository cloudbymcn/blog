Meu dia de trabalho virou: três ou quatro agentes de código rodando em terminais, um editor aberto ao lado, notas em Markdown em outra janela, e eu copiando a saída de um agente para dentro do outro. O gargalo não era o modelo; era eu fazendo papel de barramento de mensagens.

O Nexus é um app desktop pessoal para Windows que junta as três coisas: um **canvas de agentes** com orquestrador, **edição de arquivos** e **conhecimento em Markdown**. Eu escrevo um pedido; o orquestrador cria uma especificação, divide em tarefas e delega aos agentes conectados, sem eu copiar nada de terminal para terminal.

## Princípio inegociável: nada na tela é inventado

> Estado, modelo, mensagem e arquivo alterado só aparecem quando vêm de um evento real do agente ou do disco. Quando a integração não permite confirmar algo, a UI mostra **"não confirmado"**, não um palpite.

Isso vale até para animação: a conexão entre dois nós no canvas só pulsa quando houve envio real. Parece detalhe, mas é o que separa uma ferramenta de orquestração de uma demonstração bonita. Se o canvas mente uma vez, eu volto a conferir tudo no terminal.

## Adaptadores nativos, não ACP

Existe um protocolo comum entre agentes (ACP). Avaliei e decidi não usar como base: cada agente tem uma interface própria mais rica que o mínimo comum.

| Agente | Interface usada |
| --- | --- |
| Claude Code | Agent SDK, com aprovação interativa via `canUseTool` |
| Codex | `app-server` por stdio (JSON-RPC, NDJSON), com fallback para `exec --json` |
| Antigravity | CLI com entrada e saída `stream-json` |

Antes de escrever código, os três protocolos foram testados de verdade e o schema do app-server do Codex foi gerado e versionado (104 métodos JSON-RPC). As evidências estão num documento de pesquisa no repositório.

## Capacidades declaradas, inclusive o que falta

Todo adaptador implementa a mesma interface e **declara** o que realmente suporta: cancelar, redirecionar em andamento, retomar sessão, listar modelos, aprovações interativas, anexos, uso de tokens. A UI lê essa declaração e mostra no cartão do agente, **inclusive os ✗ e ⚠**.

<Callout type="warn">

**Sem fingir paridade.** O Antigravity não cancela por protocolo; cancelar é matar o processo, e o cartão diz isso. Também não tem aprovação interativa, só política pré-configurada. Anexos aparecem como "não confirmado". É melhor ver a limitação do que descobrir no meio de uma tarefa.

</Callout>

## Paralelismo sem pisar no pé

<Steps>
<Step n={1}>

Em repositório Git, cada tarefa paralela roda no **próprio `git worktree`**.

</Step>
<Step n={2}>

**Dois agentes nunca escrevem o mesmo arquivo.** O planejador detecta sobreposição entre tarefas e serializa ou divide o escopo.

</Step>
<Step n={3}>

Há um **responsável explícito pelo merge**; por padrão, o orquestrador.

</Step>
</Steps>

## Estado em SQLite, conhecimento em Markdown

O estado operacional (histórico, layout do canvas, grafo de tarefas, sessões) fica em `node:sqlite`, embutido no Node do Electron: sem ORM, sem dependência nativa extra. O que eu leio e versiono fica em **Markdown real dentro do projeto**: pedido, especificação, plano, registro de execução e resultado, um arquivo por etapa.

O registro de execução lista só eventos observáveis, com hora e tarefa: "schema gerado, 39 arquivos", "binário localizado em tal pasta", "teste dos 3 protocolos: saída X". Sem raciocínio interno de modelo.

## Stack

Electron 44 com `node-pty` (processos de agente e PTY no processo main), electron-vite + Vite, React 19 + TypeScript, React Flow no canvas, Monaco no editor, xterm.js no terminal, zustand, `motion`, Tailwind 4 com tokens próprios e chokidar para observar o disco. Sem Redux, sem ORM, sem biblioteca de componentes pronta. O instalador é um `.exe` NSIS de ~118 MB, o formato que o `electron-updater` atualiza.
